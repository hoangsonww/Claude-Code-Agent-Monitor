# Architecture Assessment: Project-wide Focus Calendar Board

## 1. Affected subsystems & boundaries

| Layer | File(s) | Current role |
|---|---|---|
| Report math (single source of truth) | `server/lib/focus-report.js` | `buildFocusSegments` → `buildSessionFocusReport` → `buildProjectFocusReport`. **Already session-list-agnostic**: `buildProjectFocusReport(dbModule, sessions)` takes a plain array of `{id, name, cwd, started_at, ended_at}` rows and has zero knowledge of "project" as a concept. It does not do any cwd/project filtering itself. |
| Session-selection / scoping | `server/routes/projects.js` (`GET /:id/focus-report`, lines 218–235) | Owns turning a `project_id` into a `cwds` list (via `project_paths`) and a `sessions` query (`WHERE cwd IN (...)`), then hands the rows to `buildProjectFocusReport`. This is the *only* place that currently decides "which sessions count." |
| Cross-machine scope filter (established, parallel convention) | `server/lib/source-filter.js` (`parseSources`, `sourceColumnClause`, `sessionIdInSourcesClause`), consumed by `server/routes/analytics.js`, `agents.js`, `events.js` | The project's actual "single source of truth for a cross-cutting filter" pattern: every other aggregate/scoped GET route accepts `?sources=` and narrows via this shared helper. **`projects.js`'s focus-report route does not call this at all** — it is the one scoped-looking endpoint that silently ignores the Remote Data Sources feature. |
| Calendar renderer (pure, stateless) | `client/src/components/FocusCalendarView.tsx` | Takes one prop, `report: FocusReport`. No fetch, no project/session awareness — literally just draws whatever `report.sessions[]` it's given. Already reused as-is by List/Calendar toggle inside the modal, off the *same already-fetched* report object (per its own file header and project memory `holistic-focus-history`). |
| Report chrome (stat tiles, list body, fetch) | `client/src/components/FocusReportModal.tsx` | Owns the `useEffect` fetch (`api.projects.focusReport(projectId)`), the stat tiles, the List/Calendar toggle, and the list-view breakdown (`ReportBody`, `ListView`, `StatTile`, `SegmentedBar`) — **none of these are exported**; they're private functions in this one file. |
| Nav/route wiring | `client/src/components/Sidebar.tsx` (`NAV_KEYS` array) + `client/src/App.tsx` (`<Route>` table) + `client/src/i18n/locales/*/nav.json` | Two flat, hand-synced lists, no registry. Trivial to extend; not itself a design risk. |
| Global remote-scope selector | `client/src/lib/dataScope.ts`, `client/src/lib/api.ts` (`activeSourcesParam`) | Automatically appends `?sources=` to "scoped GET" calls. `api.projects.focusReport` currently goes through `request()` the same as everything else, so it *would* pick up `?sources=` automatically at the client layer — but the server route ignores the param entirely, so today it's a silent no-op on the existing per-project focus report. |

## 2. Current design

The report pipeline is already well-factored around a single computation path: one session query → `buildSessionFocusReport` per session → `buildProjectFocusReport` aggregates. The client mirrors this discipline for the *List vs Calendar* toggle specifically — one fetch produces one `FocusReport` object, and `FocusCalendarView` / `ListView` are two renderers of the same object, not two fetches (this is explicitly called out as the approved v1 design in the `holistic-focus-history` project memory).

Where the current design does **not** yet follow that discipline is one layer up: the *chrome* around the report (stat tiles + List/Calendar toggle + `ListView`) is not its own reusable unit — it's private to `FocusReportModal.tsx`. There is exactly one caller of that chrome today (the modal), so this has never been forced into the open. Adding a second entry point (the standalone board) is exactly the change that will expose it.

Scoping today is single-purpose and inline: `projects.js` resolves `project_id → cwds → sessions` with one query, with no session filter, no cross-project aggregation, and — distinctly from `analytics.js`/`agents.js`/`events.js` — no `sources` filtering, even though the client-side `request()` helper already appends `?sources=` to this call for free. That's a pre-existing, if currently invisible, gap in this project's own "one filter helper, every scoped endpoint uses it" convention.

## 3. Options for the data-access path

**Option A — "Quick": client-side merge of N per-project reports.**
Structurally worse than it first appears: `GET /api/projects/:id/focus-report` requires a `:id` in the path, so there is no way to express "no project selected / all projects" without first calling `GET /api/projects` and then fan-out fetching every project's report (N+1, worse under growth). Session-level filtering would have to be reimplemented client-side against data the server already knows how to select correctly (cwd→project_paths join), and `sources` scoping would need a *second*, client-side reimplementation of logic that already exists server-side in `source-filter.js`. This recreates, on the client, a second copy of "which sessions belong to this view" — the same shape of duplicated-logic risk this project's own domain pattern (one fetch → one report → shared renderers) is already built to avoid for List vs. Calendar. Reject.

**Option B — "Proper": new aggregate endpoint, `buildProjectFocusReport` reused unchanged.**
Add a new top-level route (not nested under `/projects/:id`, since "all projects" must be representable) accepting `?project_id=&session_id=&sources=`. Contrary to the brief's framing, **`buildProjectFocusReport` itself needs no generalization** — it already only consumes a `sessions` array. The actual work is entirely in a new route-layer query that resolves the right session rows (all sessions, or filtered by project's cwds, or filtered to one `session_id`), reusing — not re-deriving — the existing cwd/`project_paths` lookup currently inline in `projects.js`, and applying `parseSources`/`sourceColumnClause` from `server/lib/source-filter.js` the same way every other cross-cutting GET does. One request, filters applied where the data already lives, follows this codebase's own established scoping convention. This is the option that strengthens (rather than forks) the single source of truth.

**Option C — hybrid.** Not viable as a distinct option: there is no way to bolt "all projects" onto a path-scoped `:id` route, so some new top-level route is unavoidable regardless of how much of Option A's client-merge idea is kept. Not worth pursuing as a middle ground.

## 4. Architectural risks

- **Response-shape drift for the new endpoint.** The existing route wraps the report as `{ project_id: project.id, ...report }`. A single `project_id` field doesn't describe an aggregate/multi-project response. The new endpoint should return `project_id`/`session_id` echoing back whatever filter was actually applied (`null` when unfiltered), not silently repurpose the field — and the shared `FocusReport` TS type needs an explicit, additive home for this rather than the client inferring meaning from a field that means something different in two contexts.
- **Per-session project attribution is currently only a raw `cwd`, not a project id/name.** `buildSessionFocusReport` returns `cwd` per session but never resolves it to a project — that resolution only happens in the route today, and only for the single project being requested. An aggregate view spanning many projects, with sessions interleaved into the same swimlane, needs a project label to disambiguate concurrent, same-looking session names — this is an additive field the new endpoint (or a thin client-side cwd→project lookup already available via `api.projects.list()`) needs to supply; it is not free.
- **`FocusCalendarView` is reusable as-is at the prop-contract level (`report: FocusReport`, nothing else) but not fully sufficient as-is for the "all projects" case.** It renders `session.name`/`session.session_id` but never shows which project a block belongs to. For a single-project report this is fine (props stay unchanged); for a cross-project aggregate, two unrelated sessions can look identical in the hover popup/label. Needs a small, additive enhancement (e.g., an optional project label surfaced on the block/popup when the report spans more than one project), not a rewrite.
- **Performance ceiling removed.** Project-scoping today bounds the sessions query to one project's folders. An unfiltered aggregate query has no such bound, and `buildSessionFocusReport` issues two extra queries per session (full event list + Focus-event list). A long-lived install with many projects/sessions could make the unfiltered "all projects, all time" default meaningfully heavier than any existing focus-report call. This dovetails with the still-open "time-window" thread already recorded in the `holistic-focus-history` project memory (14-day-ish default window for per-session lists) — not required to resolve for v1, but the same pressure point reappears here and is worth flagging to the PM/PO rather than silently deferring twice.
- **Remote-sources scoping consistency.** If the new endpoint skips `?sources=` (mirroring the old endpoint's gap), it creates a *second* instance of the same inconsistency, this time on a first-class sidebar destination where users are more likely to expect the global Data Scope selector to apply (Dashboard/Analytics honor it; this new board sitting as their peer should too). Recommend the new endpoint apply `source-filter.js` from day one; treat retrofitting the *old* per-project endpoint as a separate, explicitly-flagged follow-up rather than silently bundling a behavior change into this ticket (per CLAUDE.md's "preserve existing behavior unless explicitly requested").
- **Two-entry-path drift (the risk the brief itself names) is real, but one level higher than it states.** `FocusCalendarView` alone is already safe (stateless, single renderer). The actual duplication risk is the *chrome around it* — stat tiles, List/Calendar toggle, `ListView` — which today exists in exactly one, non-exported place (`FocusReportModal.tsx`). Building the new page by copy-pasting that chrome (rather than extracting it) would be the concrete way this project reintroduces the "same content, two codepaths, drift over time" shape its own working guide is generally wary of.
- **Docs/i18n surface.** New route needs `docs/API.md` entry; new nav entry needs a label key added across all four locales (`en/zh/vi/ko` per `SUPPORTED_LANGUAGES` in `Sidebar.tsx`), not just `en`. New page needs a snapshot added to `client/src/pages/__tests__/screens.snapshot.test.tsx`.

## 5. Recommended approach

Option B, implemented as:

- **Server:** new top-level route (its own `server/routes/focus-report.js`, since this endpoint isn't really project-scoped-by-path the way `projects.js`'s other routes are) exposing `GET /api/focus-report?project_id=&session_id=&sources=`. Factor the "resolve session rows for a project_id, or all, optionally filtered by session_id" query out of `projects.js` into one shared helper both routes call — do not hand-copy the `project_paths`/cwd-join SQL a second time. Apply `parseSources`/`sourceColumnClause` (`server/lib/source-filter.js`) on the new route's session query, matching the established convention used by `analytics.js`/`agents.js`/`events.js`. `buildProjectFocusReport`/`buildSessionFocusReport` in `focus-report.js` need no changes.
- **Client:** extract `FocusReportModal`'s stat tiles + List/Calendar toggle + `ListView` into a shared component (e.g. `FocusReportBody.tsx`) that both `FocusReportModal` (wrapped in the existing modal chrome) and a new standalone page (wrapped in page chrome with project/session filter controls above it) render from — one implementation of "how a `FocusReport` renders," not two. `FocusCalendarView` itself needs one small additive change: optional project-label context on blocks/hover-popup for the case where `report.sessions` spans more than one project.
- **Nav/route:** one new `NAV_KEYS` entry + one new `<Route>`, matching the existing pattern exactly — no structural risk there.
- **Filter defaults:** "all projects" is the default aggregate state (no project required first); session filter, when present, scopes to whichever project is currently selected rather than listing every session dashboard-wide.

This is the option that preserves and strengthens the one place this project already treats as ground truth for report math (`focus-report.js`), extends (rather than forks) the one place it already treats as ground truth for cross-machine scoping (`source-filter.js`), and — by extracting the report chrome instead of letting the new page copy it — closes the exact "same content, two entry paths, no shared implementation" gap the brief flags, before it has a chance to drift.
