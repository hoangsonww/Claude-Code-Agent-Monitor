# Agent Dashboard para Claude Code, Cursor e Codex

### Plataforma de monitoramento em tempo real da atividade dos agentes do Claude Code, Cursor e Codex 🚀

Um painel profissional para acompanhar e visualizar em tempo real as sessões dos agentes do Claude Code, Cursor e Codex: uso de ferramentas, histórico de conversas, custo e orquestração de subagentes. Feito com Node.js, Express, React e SQLite, ele combina hooks nativos com a descoberta local de transcrições específica de cada provedor.

## Visão geral

Acompanhe sessões, monitore agentes em tempo real, visualize o uso de ferramentas, reveja conversas e observe a orquestração de subagentes por uma interface web profissional com tema escuro. O Claude Code e o Codex usam seus hooks nativos; o Cursor vem incluído de fábrica por meio de eventos ao vivo compatíveis e da descoberta nativa de transcrições em `~/.cursor`.


```mermaid
graph LR
    A["Sessão do<br/>Claude Code / Cursor"] -->|hooks + descoberta local<br/>de transcrições| B["Hook Handler + Sync do Cursor<br/>(Node.js)"]
    X["Sessão do<br/>Codex"] -->|hooks + rollout JSONL| B
    B -->|HTTP POST| C["Servidor do painel<br/>(Express + SQLite)"]
    C -->|broadcast<br/>WebSocket| D["Interface do painel<br/>(React + Tailwind)"]
    style A fill:#6366f1,stroke:#818cf8,color:#fff
    style B fill:#1a1a28,stroke:#2a2a3d,color:#e4e4ed
    style C fill:#1a1a28,stroke:#2a2a3d,color:#e4e4ed
    style D fill:#10b981,stroke:#34d399,color:#fff
```

Além do painel de monitoramento em tempo real, o projeto inclui uma implementação local de servidor MCP em `mcp/` que expõe um catálogo de ferramentas para inspecionar e gerenciar o próprio painel, facilitando integrar as operações do painel direto nos seus fluxos do Claude Code e do Codex. Há também uma camada de extensões de agente, com plugins, skills e subagentes do Claude Code e do Codex para interagir com o painel, fazer análises e obter inteligência de fluxos.

### Internacionalização (i18n)

A interface vem com troca de idioma embutida para inglês (`en`), chinês (`zh`), vietnamita (`vi`), coreano (`ko`), espanhol (`es`) e português do Brasil (`pt`). Um menu de idiomas próprio evita que o seletor aperte a barra lateral conforme mais idiomas são adicionados. Os recursos de idioma são carregados por namespace e guardados no armazenamento do navegador, para a preferência do usuário se manter entre recarregamentos.

```mermaid
flowchart LR
    A["Usuário escolhe o idioma<br/>en / zh / vi / ko / es / pt"] --> B["Detector do i18next<br/>localStorage -> navigator"]
    B --> C["Idioma resolvido<br/>padrão: en"]
    C --> D["Recursos por namespace<br/>common/nav/dashboard/..."]
    D --> E["Hooks useTranslation do React"]
    E --> F["Interface traduzida + rótulos de acessibilidade"]
```

Para a arquitetura completa e a orientação de operação, veja [docs/I18N.md](./docs/I18N.md).

O painel cobre o ciclo de vida completo dos agentes locais. Os contratos detalhados de operação ficam nas seções indicadas e nas referências de `docs/`.

| Funcionalidade | Resumo |
| --- | --- |
| **Progresso das tarefas** | Progresso com responsáveis vindo das ferramentas de tarefa do Claude, do antigo `TodoWrite` e do `update_plan` do Codex. Prévias compactas aparecem em cartões e linhas; os Detalhes da sessão adicionam segmentos de status, trabalho ativo, responsáveis e paginação de 10 linhas. Trabalho novo de nível superior limpa o estado inacabado antigo, enquanto o histórico concluído fica. |
| **Painel** | As abas persistentes **Monitor** e **Saúde** juntam totais da frota, hierarquias ativas, atividade recente, saúde ponderada de sucesso/cache/erros/heap, armazenamento, ferramentas, modelos, eficácia dos subagentes e métricas de compactação. A Saúde atualiza a cada 5 segundos a partir de `/api/settings/info` e `/api/workflows`. |
| **Quadro Kanban** | As colunas de agentes cobrem Trabalhando, Aguardando, Concluído e Erro; as de sessões adicionam Ativas e Abandonadas. Os cartões paginam de 10 em 10, assinam só a visão WebSocket ativa, mantêm os títulos completos e explicam os motivos de espera, como pedido de permissão, fim do turno, prompt parado ou interrupção. |
| **Sessões** | Histórico com busca, filtros e paginação no servidor, com cálculo de custo da página visível e uma linha temporária em memória para o início do Codex. O seletor de provedor filtra Claude Code, Cursor ou Codex respeitando o escopo de produto escolhido na primeira execução ou em Configurações. A busca cobre `id`, `name` e `cwd` com espera de 300 ms. Os nomes vêm do título explícito, do título da IA e, por fim, do primeiro prompt relevante do usuário. O Cursor troca um nome provisório tirado do primeiro prompt pelo título nativo gerado só quando os metadados de coleta provam que o CCAM é dono do nome atual; nomes manuais e nomes antigos ambíguos ficam como estão. |
| **Detalhes da sessão** | Estatísticas ao vivo, trabalho ativo, uso de ferramentas, subagentes, tokens, hierarquia, linhas do tempo de eventos filtradas, agrupamento por `tool_use_id` e renderizadores específicos de cada ferramenta. A visão de conversa mostra turnos em fila, avisos do sistema, Markdown, código destacado e ferramentas estilizadas; as faixas de espera mostram o motivo e o tempo decorrido. |
| **Feed de atividade** | Eventos em tempo real que podem ser pausados, com filtros compartilhados, paginação no servidor, agrupamento, origem por projeto/sessão/subagente, links para a sessão e selos de status consistentes entre Claude e Codex. |
| **Análises** | Tokens por modelo, frequência de ferramentas, mapas de calor de atividade alinhados ao domingo, tendências de sessões, estado da conexão, esqueletos de carregamento no mesmo layout e legendas longas paginadas. |
| **Paleta de comandos** | `Cmd/Ctrl+K` busca comandos recentes, todas as rotas, sessões ao vivo no servidor, ações da página, pastas de projeto, subvisões, filtros, Configurações, Config. do agente, preferências, escopo e idioma. Ela tem ranking por subsequência, escopos `>`/`@`/`#`, controle total pelo teclado, rótulos traduzidos, falha silenciosa da busca e só navega (não executa) em ações destrutivas. |
| **Um só atalho** | `Cmd/Ctrl+K` é o único atalho global do painel, inclusive dentro de campos. A navegação por várias teclas foi removida para evitar modos escondidos; o Tabby mantém `Cmd/Ctrl+B`. |
| **Atualizações ao vivo** | O push por WebSocket atualiza a interface sem polling. |
| **Descoberta automática** | Os sinais dos provedores criam sessões e agentes automaticamente. O Claude aparece no `SessionStart`; o Codex mostra um cartão local temporário em Aguardando antes de existir um ID durável, adota com segurança threads concluídas retomadas e nunca grava cartões sem identidade nos totais duráveis, análises, alertas ou notificações. |
| **Importação de histórico** | As transcrições do Claude em `~/.claude/` e os rollouts do Codex em `~/.codex/sessions` usam fluxos de leitura e envio específicos de cada provedor, a mesma contabilidade da coleta ao vivo e gravações idempotentes. Rollouts externos do Codex ganham uma cópia para as conversas sobreviverem à remoção da origem. |
| **Hierarquia de subagentes** | Árvores pai-filho recolhíveis no Painel e nos Detalhes da sessão se expandem sozinhas enquanto os filhos estão ativos. |
| **Agentes em segundo plano** | Subagentes em segundo plano continuam acompanhados sem conclusão antecipada. |
| **Atribuição de ferramentas a subagentes** | O `SubagentStop` e as leituras na inicialização importam as ferramentas do JSONL de cada subagente, pareiam resultados por `tool_use_id`, removem duplicatas, juntam linhas ao vivo correspondentes dentro de 30 segundos e reconstroem os pais aninhados reais a partir dos IDs dos filhos criados. A troca de pai é aditiva e atualiza a interface mesmo quando nenhuma linha é inserida. |
| **Controle de custos** | Estimativas equivalentes à API—não cobranças de assinatura—usam tarifas configuráveis por modelo, incluindo o modelo nativo concreto do Cursor e um registro de uso por geração. Um ícone de informação acessível ao lado de cada rótulo de custo no Painel e nas Análises mostra o escopo escolhido e cada tarifa que falta; o tooltip do valor nas Análises traz só o valor exato, e as Configurações mostram os mesmos detalhes de cobertura na própria tela. |
| **Cache de transcrições** | A leitura incremental de JSONL extrai tokens, compactações, erros de API, duração dos turnos, raciocínio e metadados de uso; leituras completas consertam duplicatas antigas, enquanto as leituras do final só acrescentam. As listas são limitadas por `TRANSCRIPT_CACHE_MAX_ARRAY_LEN`, padrão `1000`, e as entradas guardam só os metadados do arquivo mais o resultado processado. |
| **Retenção de cópias de transcrições** | Cópias duráveis do Claude, Codex e Cursor preservam a conversa mais completa. As cópias do armazenamento nativo do Cursor mantêm a raiz ao vivo, as referências só antigas e os blobs brutos exatos delas, deixando de fora o histórico inalcançável. Um worker isolado migra no máximo quatro armazenamentos só antigos por sincronização; os armazenamentos de origem abrem só para leitura, uma trava por sessão serializa as instalações e uma leitura agendada vazia espera cinco minutos antes de checar de novo. Depois de cinco falhas para a mesma marca de origem num processo, o arquivo fica para conserto posterior. Só as cópias JSONL elegíveis do Claude/Cursor cuja origem sumiu são compactadas com gzip depois de uma ida e volta verificada; as cópias do Codex ficam sem compactar. A limpeza remove cópias, e limites opcionais de idade/tamanho podem apagar a única cópia antiga depois de uma prévia em Configurações. |
| **Notificações** | O Web Push com VAPID entrega os eventos configurados com o navegador em segundo plano ou fechado, com suporte a áudio no macOS e controles de assinatura. |
| **Alertas** | As Configurações têm Regras, Canais e Atividade para alertas de padrão de evento, inatividade, agente travado e tokens. As regras de evento rodam depois da coleta; as regras de tempo varrem a cada 60 segundos. Os alertas gravados usam intervalo mínimo por regra/sessão, padrão 300 segundos, entrega por WebSocket, reconhecimento e envio por webhook com escopo para 14 provedores com nome ou JSON genérico assinado, com segredos mascarados, tempos limite e novas tentativas limitadas. |
| **Aviso de atualização** | Um `git fetch` agendado que não bloqueia compara o checkout com o remoto oficial e mostra o comando exato de atualização na janela, na barra lateral e no terminal. O CCAM nunca faz pull nem se reinicia sozinho. |
| **Configurações** | Status do sistema e dos hooks, preços por provedor, notificações, limpeza, pastas dos provedores, atualização instantânea dos dados e restauração idempotente de JSON exportado de até 25 MiB. Os preços têm padrões por provedor, regras com curinga, orientação sobre tarifas publicadas, o limite de 272K do GPT e catálogos separados de modelos nativos do Cursor e de terceiros. |
| **Executar agente + Config. do agente** | `/run` inicia o Claude Code ou threads nativas do app-server do Codex com modelos, aprovações, sandbox, retomada, parada, streaming e reconexão específicos de cada provedor. `/cc-config` junta exploradores editáveis do Claude e do Codex; os arquivos de usuário suportados usam gravações atômicas protegidas e backups com data e hora, prévias com segredos ocultos, comandos de perfil exatos e observadores por provedor. |
| **Config. do agente do Codex** | Mostra o catálogo completo de modelos da conta mais os ajustes da base/dos perfis, cria sobreposições padrão `<name>.config.toml` e protege a edição com checagens canônicas de contenção e de links simbólicos. Perfis, hooks, regras, skills e instruções têm ações de origem/caminho/edição/exclusão com backup antes de excluir; o `config.toml` só pode ser editado. |

Um único catálogo validado exige alvos localhost ou HTTPS, regras de bearer token, recusa de redirecionamentos, travas de alteração, envios de 50 MiB por arquivo e 100 MiB por chamada, respostas binárias de 10 MiB e restaurações de 25 MiB. |
| **Fluxos** | Onze seções em D3 cobrem orquestração, fluxo de ferramentas, colaboração, eficácia, padrões, delegação, erros, concorrência, complexidade, compactação e detalhe da sessão. Tooltips explicativos traduzidos, filtro cruzado, exportação JSON, atualização ao vivo com espera de 3 segundos e execuções dinâmicas reconstruídas dos diários preservam fase, tokens, ferramentas, duração, prompt e resultado de cada agente. |
| **Acompanhamento de compactações** | As leituras de transcrições criam agentes/eventos de compactação com duração zero, consertam durações negativas antigas, completam sessões antigas e inspecionam periodicamente só as sessões ativas pelos valores em cache de `sessions.transcript_path`. |
| **Subsessões/Sessões retomadas** | A correlação pelo `generation_id` do Cursor liga uma sessão de shell do `/resume` à conversa oficial dela, redireciona links de sessão antigos e remove hooks de conclusão repetidos. Outros eventos novos reativam sessões retomadas ou órfãs; a varredura limitada de sessões paradas continua pegando as abandonadas. |

Só arquivos novos ou que avançaram são reprocessados, com escopo de observador seguro no Linux e broadcasts das sessões ao vivo. |

## Início rápido

### Pré-requisitos

- **Node.js** >= 22.22.0 (recomendado 24 LTS)
- **npm** >= 9.0.0

### 1. Instalar

```bash
git clone https://github.com/hoangsonww/Claude-Code-Agent-Monitor.git
cd Claude-Code-Agent-Monitor
npm run setup
```

### 2. Configurar os hooks do Claude Code

```bash
npm run install-hooks
```

Escolha **Claude Code**, **Codex (beta)** ou os dois com as setas, Espaço e Enter. Por padrão, os hooks do Claude ficam em `~/.claude/settings.json` e os do Codex em `~/.codex/hooks.json`. Reinstalar substitui só as entradas do CCAM e preserva os outros hooks; a mesma ação está em **Configurações → Configuração dos hooks**.

A pasta do Claude segue `CLAUDE_HOME || CLAUDE_CONFIG_DIR || ~/.claude`, então os hooks e as transcrições usam a pasta realocada. Com `CLAUDE_CONFIG_DIR`, a Config. do agente lê `$CLAUDE_CONFIG_DIR/.claude.json`. A descoberta usa os dados de app locais da máquina sempre que a pasta do Claude é realocada. Para os dados do painel, uma pasta local da máquina que já existe vence; senão, uma `<CLAUDE_HOME>/agent-dashboard` ou `~/.claude/agent-dashboard` existente é reaproveitada, e dados novos usam os dados de app locais da máquina. `DASHBOARD_DATA_DIR` permite escolher outro caminho local. `CCAM_NO_AUTO_HOOKS=1` pula a instalação na inicialização e deixa as entradas antigas como estão; a instalação manual continua funcionando, e uma entrada antiga com handler faltando deve ser reinstalada ou removida. Caminhos de hook instalados pela versão atual saem em silêncio e aparecem como não instalados se o handler sumir. Nas Configurações do app de desktop empacotado, os ajustes de pasta são salvos no `userData/.env` do Electron quando ele é dono do servidor; um servidor adotado usa o próprio arquivo de ambiente. Em desenvolvimento vale o `.env` do repositório.

Na primeira execução, o CCAM verifica só os provedores escolhidos no escopo de dados atual e oferece instalar os hooks que faltam. Se a verificação falhar, ele volta para a configuração manual em vez de bloquear o painel.

A descoberta dos provedores continua depois da configuração:

- **Claude Code e Cursor:** os hooks do Claude alimentam os eventos ao vivo. O CCAM junta automaticamente os comandos `stop` e `afterAgentResponse` dele no `~/.cursor/hooks.json` sem substituir nem quebrar cadeias de comandos de terceiros; rode `npm run install-cursor-hooks` para consertá-los à mão. O armazenamento de chat nativo e o observador de transcrições do Cursor continuam como plano B offline, correlacionam IDs de shell do `/resume` com as conversas oficiais, juntam o histórico de prompts do armazenamento nativo, do JSONL e dos apelidos, adotam títulos gerados só para nomes que pertencem à coleta, resolvem `default` só quando há uma resposta correspondente em algum armazenamento nativo da família de apelidos e respeitam `DASHBOARD_CURSOR_HOME`.
- **Codex:** os hooks e o acompanhamento incremental dos rollouts em `~/.codex/sessions` mantêm atualizados o ciclo de vida, prompts, títulos, ferramentas, tokens, custos, compactações, conversas e o estado do WebSocket. Arquivos com problema são tentados de novo isoladamente; a correspondência exata entre rollout e processo evita cartões ativos fantasmas; os títulos nativos do `/rename` e o histórico de conversa paginado por cursor continuam ao vivo.
- **Ambos:** os cartões mantêm os dois últimos prompts humanos distintos, mostram anexos de imagem gravados e removem respostas repetidas do Codex. O escopo só Codex esconde os diários de Workflows dinâmicos que são só do Claude.

### Alternativa: Docker / Podman

A imagem OCI e os arquivos Compose funcionam com Docker e Podman. O runtime não roda como root, descarta todas as capabilities, usa o Tini como PID 1, inclui Git/OpenSSH/SQLite e fica só leitura, exceto `/app/data`, `/app/config` e `/tmp`.

```bash
# Dashboard only
docker compose up -d --build
# or
podman compose up -d --build

# Complete stack: dashboard + authenticated MCP + Nginx + Prometheus + Grafana
umask 077
openssl rand -hex 32 > deployments/secrets/dashboard-token
openssl rand -hex 32 > deployments/secrets/hook-token
openssl rand -hex 32 > deployments/secrets/mcp-token
openssl rand -base64 32 > deployments/secrets/grafana-admin-password
npm run docker:full:up
```

Todas as portas do host ficam presas ao loopback por padrão: painel `4820`, MCP `8819`, Nginx `8080`, Prometheus `9090` e Grafana `3000`. As pastas do Claude e do Codex são montadas só leitura; volumes nomeados guardam o SQLite e a configuração própria do painel. O Nginx faz proxy da interface, da API REST autenticada e do WebSocket, enquanto hooks, métricas e MCP ficam bloqueados na borda, a menos que sejam ligados explicitamente. O alvo Docker opcional `agent-runtime` adiciona as CLIs do Claude Code e do Codex em versões fixas para fluxos de Executar agente dentro do contêiner.

> [!IMPORTANT]
> Instale os hooks do Claude Code/Codex no host depois que o contêiner subir, com `npm run install-hooks -- --both --dashboard-port 4820` (troque `4820` se publicou outra porta no host). O instalador grava esse alvo verificado porque o contêiner só leitura não consegue publicar uma entrada de descoberta visível no host. Quem já usa o Compose deve rodar este comando uma vez depois de atualizar, para as entradas de hook antigas do painel receberem o alvo explícito. Para hooks remotos na nuvem, defina `CCAM_DASHBOARD_URL=https://...` e um `CCAM_HOOK_TOKEN` separado; URLs de hook fora do loopback exigem HTTPS. Veja [DEPLOYMENT.md](DEPLOYMENT.md).

## Como funciona


O painel se integra ao Claude Code pelo sistema de hooks nativo dele para monitorar a atividade dos agentes em tempo real. Esta é uma visão geral da arquitetura e do fluxo de dados:

```mermaid
sequenceDiagram
    participant CC as Claude Code
    participant HH as Hook Handler
    participant API as Servidor Express
    participant DB as SQLite
    participant WS as WebSocket
    participant UI as Client React

    CC->>HH: stdin (evento JSON)
    HH->>API: POST /api/hooks/event
    API->>DB: Insere/atualiza registros
    API->>WS: Broadcast da atualização
    WS->>UI: Envia mensagem
    UI->>UI: Re-renderiza o componente

    Note over CC,HH: Hooks disparam em SessionStart,<br/>PreToolUse, PostToolUse,<br/>Stop, SubagentStop,<br/>SessionEnd, Notification.<br/>Compactação detectada no JSONL
    Note over API,DB: Gravações em transação<br/>com criação automática de sessão/agente
    Note over WS,UI: Latência de ~0ms,<br/>sem polling
```

> [!IMPORTANT]
> Veja [ARCHITECTURE.md](./ARCHITECTURE.md) para um mergulho na arquitetura do servidor, esquema do banco, rotas da API, design do WebSocket, roteamento do cliente, fluxo do hook handler, modos de implantação e diagramas detalhados do ciclo de vida de sessões e agentes.

### Ciclo de vida dos hooks

1. **O Claude Code** emite hooks de sessão, prompt, ferramenta, notificação, subagente, turno e saída.
2. **`scripts/hook-handler.js`** lê cada evento do stdin e mira primeiro em `CCAM_DASHBOARD_URL`, depois num `CLAUDE_DASHBOARD_PORT` explícito e então nos painéis vivos do registro local `.agent-dashboard.json`. Para uma pasta do Claude realocada por `CLAUDE_HOME` ou `CLAUDE_CONFIG_DIR`, o registro fica nos dados de app locais da máquina; para a pasta padrão, fica em `~/.claude`. Ele filtra pela pasta oficial do Claude e envia uma vez para cada diretório de dados SQLite distinto, escolhendo a menor porta quando há listeners duplicados, mas ainda alimentando painéis correspondentes com bancos separados. A entrega é à prova de falhas: cada alvo é isolado e o handler sai em até 2,5 segundos.
3. **O servidor** grava o evento e o estado relacionado numa única transação SQLite:
   - O primeiro contato cria a sessão e o agente principal. `SessionStart` começa em **Aguardando**; `UserPromptSubmit` ou `PreToolUse` passam para **Trabalhando**; `PostToolUse` mantém trabalhando.
   - `Stop` devolve o agente principal para **Aguardando** enquanto os agentes em segundo plano continuam. `stop_reason=error` marca o agente e a sessão como **Erro**. Notificações de permissão também esperam entrada; só um prompt novo ou o início de uma ferramenta recupera um erro.
   - `SubagentStop` conclui aquele filho sem mudar o estado de espera humana. Uma leitura separada importa então as ferramentas do JSONL dele, pareia usos/resultados por `tool_use_id`, remove duplicatas e reconstrói os pais aninhados reais.
   - `SessionEnd` limpa a espera e conclui a sessão, a menos que um erro precise ser preservado. Trabalho novo reativa sessões concluídas, com erro ou abandonadas, inclusive importadas e retomadas.
   - `SessionStart` e a manutenção periódica abandonam sessões inativas depois de `DASHBOARD_STALE_MINUTES`, padrão 180. A varredura roda a cada um quarto desse valor, limitada entre 60 segundos e 5 minutos.
   - A leitura incremental compartilhada das transcrições registra compactações, erros de API e de ferramentas, duração dos turnos, tokens e metadados sem reler bytes que não mudaram. As varreduras de sessões ativas usam os valores indexados de `sessions.transcript_path` e descartam entradas de cache abandonadas.
   - Um vigia de 15 segundos acha erros de API na transcrição depois de 10 segundos sem hooks. Ele também recupera interrupções com Esc pelos marcadores da transcrição ou, quando não há marcador, depois de `DASHBOARD_WORKING_IDLE_SECONDS`, padrão 120, só quando nenhuma ferramenta está rodando e nem os hooks nem a transcrição avançam.
   - O mesmo vigia conclui sessões locais mortas por uma checagem de vida do processo depois de `DASHBOARD_LIVENESS_IDLE_SECONDS`, padrão 60. As checagens da inicialização rodam na hora e de novo depois de uns 5 segundos, sem essa espera. A checagem pula Windows, contêineres, caminhos encaminhados não POSIX, sessões de fontes remotas, falhas de ferramenta e `DASHBOARD_LIVENESS_PROBE=0`; um hook real depois corrige sozinho uma conclusão errada.
   - A sincronização contínua de projetos combina uma varredura imediata, `fs.watch` com espera e polling `DASHBOARD_SESSION_SYNC_MS`, padrão 30 segundos. Um cache de mtime reprocessa só transcrições novas ou que cresceram e transmite os mesmos frames de sessão que os hooks.
4. **O WebSocket** publica a mudança gravada.
5. **A interface** atualiza as telas afetadas sem polling.

### Máquina de estados do agente

Status gravados: `working | waiting | completed | error`. A coluna
`awaiting_input_since` é complementar — ela marca quando o agente
começou a esperar e é usada para mostrar a duração, mas `waiting` agora é um
status gravado de verdade.

```mermaid
stateDiagram-v2
    [*] --> waiting: ensureSession (primeiro hook)
    waiting --> working: PreToolUse / UserPromptSubmit / Codex task_started / user_message
    working --> working: PostToolUse (ferramenta concluída)
    working --> waiting: Stop, sem erro / Codex task_complete
    working --> waiting: Codex turn_aborted (interrompido)
    working --> waiting: Notification (pedido de entrada)
    working --> waiting: Cancelar com Esc (marcador do vigia ou tempo ocioso)
    waiting --> error: Stop com erro
    working --> error: Stop com erro
    waiting --> error: Erro de API detectado (vigia)
    working --> error: Erro de API detectado (vigia)
    error --> working: UserPromptSubmit / PreToolUse (recuperação)
    working --> completed: SessionEnd
    waiting --> completed: SessionEnd

    note right of waiting
        O agente está entre turnos ou
        esperando a entrada do usuário
    end note
```

### Máquina de estados da sessão

Status gravados: `active | completed | error | abandoned`. O estado de
sessão **Aguardando** é uma camada da interface (status=`active` com
`awaiting_input_since` preenchido).

```mermaid
stateDiagram-v2
    [*] --> waiting: SessionStart startup/resume/clear (status=active + marca)
    active --> active: SessionStart compact (no meio do turno — estado preservado, sem marca)
    waiting --> active: UserPromptSubmit / PreToolUse / PostToolUse / Codex task_started / user_message
    active --> waiting: Stop, sem erro / Codex task_complete (marca renovada)
    active --> waiting: Codex turn_aborted (interrompido)
    active --> waiting: Notification de permissão (agente → waiting)
    active --> waiting: Cancelar com Esc (marcador do vigia ou tempo ocioso)
    active --> error: Stop, stop_reason=error
    active --> error: Erro de API detectado (vigia)
    waiting --> error: Erro de API detectado (vigia)
    error --> active: UserPromptSubmit / PreToolUse (recuperação)
    waiting --> completed: SessionEnd (a CLI saiu)
    active --> completed: SessionEnd (a CLI saiu)
    error --> error: SessionEnd (preserva o erro)
    waiting --> abandoned: Parada > DASHBOARD_STALE_MINUTES (padrão 180)

    error --> active: Sessão retomada (novo evento de trabalho)
    abandoned --> active: Sessão retomada (novo evento de trabalho)
    completed --> [*]
    error --> [*]
    abandoned --> [*]
```

## Configuração

| Variável de ambiente | Padrão | Para que serve |
| --- | --- | --- |
| `DASHBOARD_PORT` | `4820` | Porta do servidor Express. |
| `CLAUDE_DASHBOARD_PORT` | não definida (descoberta) | Porta explícita usada pelo hook handler; grave-a na instalação com `--dashboard-port N`. |
| `NODE_ENV` | `development` | Use `production` para servir o client compilado. |
| `DASHBOARD_UPDATE_CHECK` | ligado | Defina `0`, `false` ou `off` para desligar as verificações agendadas no upstream. |
| `DASHBOARD_UPDATE_CHECK_INTERVAL_MS` | `300000` | Intervalo de verificação de atualização, mínimo de 60.000 ms. O **Verificar agora** manual continua disponível. |
| `DASHBOARD_STALE_MINUTES` | `180` | Tempo de inatividade antes de uma sessão ativa ou em Aguardando virar abandonada. O vigia aplica a regra e a manutenção roda a cada um quarto desse valor, limitada entre 60 segundos e 5 minutos. |
| `DASHBOARD_WORKING_IDLE_SECONDS` | `120` | Recupera um cancelamento com Esc sem marcador quando nenhuma ferramenta, hook ou atividade de transcrição avança. Valores menores reagem mais rápido, mas podem classificar errado por um tempo turnos longos e silenciosos; atividade nova corrige sozinha. O Cursor usa a mesma regra. |
| `DASHBOARD_LIVENESS_PROBE` | `1` | Defina `0` para desligar a conclusão por processo de sessões locais mortas do Claude/Codex. Pula automaticamente Windows, contêineres, caminhos encaminhados não POSIX e fontes remotas. |
| `DASHBOARD_LIVENESS_IDLE_SECONDS` | `60` | Espera de inatividade da transcrição ou do último hook para as checagens de vida do vigia. As checagens da inicialização ignoram a espera, para sessões já mortas sumirem na hora. |
| `DASHBOARD_SESSION_SYNC_MS` | `30000` | Polling de segurança para arquivos novos ou alterados em `~/.claude/projects`. O `fs.watch` continua imediato; `0` desliga só o polling. |
| `DASHBOARD_CURSOR_HOME` | `~/.cursor` | Raiz do estado do Cursor para chats, transcrições, preenchimento retroativo e cópias duráveis. |
| `DASHBOARD_CURSOR_SYNC_MS` | `5000` | Polling de segurança do Cursor com impressão digital. Os observadores continuam ativos quando `0` desliga o polling. |
| `DASHBOARD_CODEX_HOME` | `CODEX_HOME` ou `~/.codex` | Raiz do estado do Codex. As Configurações gravam uma substituição, religam a observação e leem na hora. |
| `DASHBOARD_CODEX_SYNC_MS` | `4000` | Polling de segurança dos rollouts do Codex. Hooks e observadores continuam ativos quando definido como `0`. |
| `DASHBOARD_CODEX_MAX_ATTEMPTS` | `5` | Tentativas para um rollout ilegível que não mudou, contando a primeira. Uma mudança de tamanho ou mtime reinicia a cota; ao esgotar, registra no log uma vez. |
| `DASHBOARD_CODEX_HOOK_IDLE_SECONDS` | `60` | Conclui sessões do Codex só com hooks, como `codex exec --ephemeral`, quando um `stop` que informou fim nunca recebe `SessionEnd`. Só o silêncio nunca basta. |
| `DASHBOARD_TASK_SUMMARY_TTL_MS` | `2000` | Janela de reaproveitamento de dados antigos para resumos de tarefas e `todo_snapshot`. Acréscimos são processados de forma incremental; crescimento acima de 32 MiB recomeça de um final novo. `0` processa cada acréscimo. |
| `DASHBOARD_SNAPSHOT_COMPRESS` | `1` | Defina `0`, `false` ou `off` para parar a conversão gzip verificada de cópias do Claude/Cursor paradas há 24 horas cuja origem sumiu. Árvores de origem ilegíveis e cópias do Codex são puladas. |
| `DASHBOARD_SNAPSHOT_MAX_AGE_DAYS` | não definida | Passada opcional de retenção a cada seis horas para sessões terminadas mais velhas que essa idade. Sessões apagadas ficam marcadas; sessões retomadas ficam protegidas. Veja a prévia com `ccam snapshots prune --days N`, porque a cópia pode ser a única. |
| `DASHBOARD_SNAPSHOT_MAX_BYTES` | não definida | Limite opcional do total de cópias em bytes ou em unidades como `5GB`. As sessões terminadas mais antigas são apagadas primeiro; sessões ativas ou das últimas 24 horas ficam protegidas. |
| `DASHBOARD_REMOTE_SYNC_MS` | `15000` | Polling das fontes remotas por SSH para projetos do Claude, rollouts do Codex e índices de títulos do Codex. Fontes novas ou religadas sincronizam na hora; `0` deixa só a sincronização manual. |
| `DASHBOARD_REMOTE_ACTIVE_WINDOW_MS` | `600000` | Considera ativa uma transcrição remota espelhada enquanto o último evento dela estiver dentro dessa janela, e depois a reconcilia como concluída. Provedores que falham voltam para o tratamento normal de sessões paradas. |
| `DASHBOARD_REMOTE_SYNC_TIMEOUT_MS` | `600000` | Tempo limite por fonte para o pull por SSH mais a importação. |
| `DASHBOARD_REMOTE_TEST_TIMEOUT_MS` | `15000` | Tempo limite do teste de SSH da fonte remota. |
| `DASHBOARD_HOST` | `127.0.0.1` | Interface de escuta. `0.0.0.0` expõe o serviço e registra um aviso. |
| `DASHBOARD_TOKEN` | não definida | Protege `/api/*` e o WebSocket por cabeçalho Bearer, `x-dashboard-token` ou `?token=`. O loopback é o limite de confiança padrão. |
| `DASHBOARD_TOKEN_FILE` | não definida | Token do painel vindo de arquivo, para segredos do Docker/Kubernetes; `DASHBOARD_TOKEN` tem prioridade. |
| `DASHBOARD_HOOK_TOKEN` / `DASHBOARD_HOOK_TOKEN_FILE` | não definida | Proteção independente para `/api/hooks/event` e `/api/hooks/codex` além do loopback. |
| `REMOTE_PUSH_TOKEN` / `REMOTE_PUSH_TOKEN_FILE` | não definida | Trava separada para os públicos `POST /api/hooks/ingest-batch` e `/api/hooks/ingest-transcript`. Os dois ficam desligados por padrão e nunca herdam o token de hook local. |
| `REMOTE_TRANSCRIPT_MAX_FILE_MB` | `256` | Tamanho máximo gravado, em MiB, de cada arquivo aceito pelo `ingest-transcript`; cada parte do pedido tem limite próprio de 4 MiB. |
| `DASHBOARD_ALLOWED_HOSTS` | loopback | Valores extras de `Host` HTTP e WebSocket, separados por vírgula, para a proteção contra DNS rebinding. |
| `DASHBOARD_ENV_PATH` | `.env` do repositório | Arquivo dotenv gravável usado para guardar as substituições de pasta dos provedores; em contêineres o padrão é `/app/config/.env`. |
| `CCAM_DASHBOARD_URL` | descoberta no localhost | Destino remoto dos hooks. URLs fora do loopback exigem HTTPS e um token de hook. |
| `CCAM_HOOK_TOKEN` / `CCAM_HOOK_TOKEN_FILE` | não definida | Credencial do cliente de hook enviada como `x-ccam-hook-token`. |

> [!IMPORTANT]
> Por padrão o servidor só escuta no loopback. Acesso pela rede local exige `DASHBOARD_HOST`, `DASHBOARD_TOKEN` e valores correspondentes em `DASHBOARD_ALLOWED_HOSTS`. Veja [`.env.example`](./.env.example) e [a política de segurança](./.github/SECURITY.md).

Clones do Git buscam periodicamente o remoto oficial e comparam o branch padrão dele com o checkout atual. Quando estiver atrás, o terminal e a interface mostram o comando exato de atualização manual. O CCAM nunca faz pull nem se reinicia sozinho.

## CLI `ccam`


A CLI **`ccam`** (`bin/ccam.js` → `cli/`) dá acesso ao painel de qualquer terminal por uma árvore de comandos Commander.js com opções herdadas, validação, sugestões, ajuda gerada e autocompletar no shell. `npm run setup` a vincula automaticamente. Para achar o servidor, ela confere `--server` / `CCAM_URL`, as portas configuradas, o registro de servidores vivos e, por fim, `http://127.0.0.1:4820`.

```bash
# Server
ccam status | health                  # ● running / ○ not running; version + timestamp
ccam start [--port N] | stop | restart  # background production server
ccam logs [-n N] [-f]                 # tail data/ccam-server.log
ccam open [page] [--session id]       # open the dashboard, a page, or a session
ccam repl                             # interactive shell (also: shell, i)

# Monitoring
ccam overview [--watch]               # one-screen live snapshot (alias: top)
ccam stats | kanban                   # totals + status distributions / status lanes
ccam tail [--session id] [--type T] [--tool N]   # live event feed
ccam stream [--type new_event,…]      # raw real-time WebSocket feed
ccam watch -n 5 <command …>           # re-run any command on an interval

# Data
ccam sessions [--status s] [--q text] [--cwd dir] [--sort price] [--limit n]
ccam sessions get|stats|cost|agents|events|transcripts <id>
ccam sessions transcript <id>         # the conversation as a readable chat log
ccam sessions rename <id> <name…> | update <id> | create | facets
ccam agents [list|get|update|create]  # agents; ccam session <id> = sessions get
ccam events [--type T] [--tool N] [--q text] [--from iso] | events facets

# Insights
ccam analytics                        # tokens, cost, top tools, daily sparklines
ccam workflows [session <id>]         # workflow intelligence + patterns
ccam runs [list|get <run-id>]         # Workflow-tool runs
ccam run list|history|start|follow|send|stop …   # dashboard-launched agents
ccam cost [--session id] [--daily]    # per-model cost, surcharges, unpriced models

# Alerts & webhooks
ccam alerts [--unacked] | ack <id> | ack-all
ccam alert-rules list|types|create|update|enable|disable|delete
ccam webhooks list|get|providers|deliveries|create|update|enable|disable|delete|test

# Pricing
ccam pricing [list] | set <pattern> --input N --output N [--fast-* …] [--intro-* …] | delete | reset
ccam pricing gpt|cursor [list|set|delete]   # OpenAI/Codex and Cursor rate cards

# Import & remote sources
ccam import guide|rescan|path <dir>|upload <files…>|reimport
ccam import-data <file.json>          # restore an export (idempotent)
ccam remote-sources list|get|add|update|enable|disable|test|sync|rm

# Administration
ccam doctor | info | export [file|-] | cleanup --hours N --days M
ccam snapshots [status|compress] | snapshots prune --days N   # transcript snapshots; prune dry-runs unless --apply --confirm PRUNE_SNAPSHOTS
ccam hooks [status|install] | reinstall-hooks | config claude|codex …
ccam updates [status|check] | update-check | metrics [--grep re]
ccam home [set claude|codex <path>] | push key|send|subscribe|unsubscribe
ccam api [METHOD] /api/path [--data JSON]   # any endpoint; writes need --yes
ccam mcp [stdio|http|repl] | clear-data --yes

# CLI
ccam help [command…] | commands [--json] | completion bash|zsh|fish | version
```

Os grupos listam por padrão (`ccam alerts` é igual a `ccam alerts list`); todo comando aceita `--help`; `ccam commands` mostra a árvore, e `ccam commands --json` emite o esquema legível por máquina.

- **Saída:** terminais (TTY) recebem tabelas, ícones de status, gráficos, minigráficos, árvores de agentes, visões de transcrição e ajuda colorida. Pipes recebem texto simples. `--json` ou `CCAM_OUTPUT=json` devolvem JSON estável, com NDJSON para `tail`, `stream` e `run follow`; erros usam `{"error":{"code":"…","message":"…"}}` no stderr e saem com `0` ou `1`.
- **Gravações:** use o `y/N` interativo ou `--yes`; gravações não interativas exigem `--yes`, e `clear-data` sempre exige a flag literal.
- **Modo offline:** comandos só de leitura recorrem a `data/dashboard.db`, mostram uma faixa `⚠ Offline mode` e corrigem sessões ativas mortas pela visão de vida dos processos. Comandos que só funcionam com o servidor explicam por que o painel não está disponível.
- **REPL e autocompletar:** `ccam repl` adiciona autocompletar guiado pela árvore, histórico persistente, um prompt ao vivo e os comandos embutidos `help`, `json` e `watch`, com cada linha isolada num processo filho. Ative o autocompletar do zsh com `source <(ccam completion zsh)`.

Se o `ccam` não estiver no `PATH`, rode `npm link` uma vez na raiz do repositório. Veja [docs/CLI.md](./docs/CLI.md) para o contrato completo.

### Fotos de custo antes de uma atualização

Antes de uma atualização que pode recontar o uso, tire uma foto de base só leitura, atualize e reinicie o CCAM, deixe a manutenção de inicialização terminar e então tire uma segunda foto num caminho novo e compare as duas. Mantenha os arquivos TSV privados: eles contêm identificadores de sessão e metadados de dono. A checagem sai com status 1 se a entrada, saída, leitura de cache, escrita de cache, escrita de cache de uma hora, busca na web, fetch na web, execução de código ou custo de uma sessão local existente mudar; se o dono mudar entre local e outra fonte ou provedor; ou se uma sessão local sumir. Sessões remotas e recém-adicionadas são relatadas à parte.

```bash
node scripts/cost-snapshot.js snapshot --out before.tsv
# Upgrade CCAM, restart it, and let startup maintenance finish.
node scripts/cost-snapshot.js snapshot --out after.tsv
node scripts/cost-snapshot.js compare before.tsv after.tsv --fail-on-local-change
```

Uma sincronização remota interrompida aparece como erro depois de reiniciar; o recibo da importação anterior continua disponível. A recuperação na inicialização só roda quando marcadores de vida por processo no diretório de dados SQLite compartilhado provam que este é o único painel vivo, mesmo quando os processos usam valores diferentes de `CLAUDE_HOME`; dono ausente, malformado ou concorrente adia a recuperação. Um banco ocupado é tentado de novo de forma independente, então a recuperação não consegue desligar o polling remoto. As novas tentativas remotas mantêm o erro mais recente visível enquanto checam de novo; uma sincronização bem-sucedida o limpa.

### Modos de operação do MCP

- Modo só leitura (padrão): `MCP_DASHBOARD_ALLOW_MUTATIONS=false`
- Modo administrador: `MCP_DASHBOARD_ALLOW_MUTATIONS=true`
- Painel autenticado: defina `MCP_DASHBOARD_API_TOKEN` / `_FILE` com o token do painel
- Transporte HTTP/SSE autenticado: defina `MCP_HTTP_AUTH_TOKEN` / `_FILE`; os clientes mandam autenticação bearer ou `x-mcp-token`
- Proteções de transporte: HTTP direto no loopback pode levar o token; apelidos de host de contêiner exigem HTTPS; redirecionamentos são recusados
- Proteções de payload: 50 MiB por arquivo de histórico enviado, 100 MiB no total por chamada, respostas binárias de 10 MiB e restauração de backup de 25 MiB
- Modo destrutivo: exige os dois:
  - `MCP_DASHBOARD_ALLOW_MUTATIONS=true`
  - `MCP_DASHBOARD_ALLOW_DESTRUCTIVE=true`
  - entrada da ferramenta `confirmation_token: "CLEAR_ALL_DATA"`

### Executar o Claude (`/api/run`)

Superfície HTTP para iniciar e supervisionar subprocessos `claude` a partir do painel. Proteção de mesma origem em toda rota — pedidos do navegador precisam vir de uma origem localhost; pedidos sem Origin (CLI/curl) passam. Um `cwd` informado precisa ser uma pasta absoluta existente e é canonicalizado com `realpath`. Ele pode estar fora deste repositório de propósito, para o Executar agente poder iniciar na pasta pessoal do usuário ou em qualquer projeto recente.

| Método   | Caminho                           | Descrição |
| -------- | --------------------------------- | ----------- |
| `GET`    | `/api/run`                        | Lista todas as execuções em memória (vivas + terminadas há pouco); devolve também `maxConcurrent` e `activeCount` |
| `GET`    | `/api/run/binary`                 | Confere se o `claude` está no `PATH` e onde fica — usado pela interface para mostrar um erro claro antes de iniciar |
| `GET`    | `/api/run/cwds`                   | Pastas de trabalho sugeridas: cwd do servidor do painel, `$HOME` e cwds recentes da tabela de sessões |
| `GET`    | `/api/run/files?cwd=…&q=…`        | Busca aproximada de arquivos dentro do `cwd` para o autocompletar de `@`-arquivo da página Executar. Pula `node_modules`, `.git`, `dist`, `build`, `.next`, `.cache`, `coverage` etc. O cwd é obrigatório e precisa existir; os resultados têm limite e são ordenados pela semelhança com o nome do arquivo |
| `POST`   | `/api/run`                        | Inicia uma nova execução. Corpo: `{ prompt, mode: "headless"\|"conversation", cwd?, model?, permissionMode?, resumeSessionId?, effort? }`. O modo headless põe o prompt no argv via `-p` e fecha o stdin. O modo conversa manda o prompt pelo stdin como um envelope stream-json e mantém o stdin aberto para continuações. `resumeSessionId` (só no modo conversa) adiciona `--resume <id>`; quando definido, `prompt` pode ser vazio — o iniciador pula a primeira escrita no stdin e o `claude` fica parado na conversa retomada até o usuário mandar uma continuação por `POST /api/run/:id/message`. `effort` (`low` / `medium` / `high`) vira `--effort`. O iniciador sempre passa `--output-format stream-json --verbose --include-partial-messages` para a interface mostrar as mudanças caractere a caractere. Na prática não há limite de concorrência (teto padrão 10000 — mude com `RUN_MAX_CONCURRENT`) |
| `GET`    | `/api/run/:id`                    | Estado atual da execução. `?envelopes=1` inclui o log de envelopes em memória para a interface reproduzir o histórico ao reconectar |
| `POST`   | `/api/run/:id/message`            | Manda um turno de continuação para uma conversa em andamento (só no modo conversa). Corpo: `{ text }` |
| `DELETE` | `/api/run/:id`                    | Para uma execução. SIGTERM, subindo para SIGKILL depois de 5 s |

A saída vai pelo WebSocket já existente do painel em três tipos de mensagem: `run_stream` (envelope stream-json processado, incluindo as mudanças `stream_event` do `--include-partial-messages`), `run_status` (mudanças de status), `run_input_ack` (escrita no stdin confirmada). A página do Explorador de configuração assina uma quarta mensagem — `cc_config_changed` — transmitida por `server/lib/cc-watcher.js` (via `fs.watch` em `~/.claude/`) e por `routes/cc-config.js` depois de todo PUT/DELETE bem-sucedido, com payload `{ source: "dashboard"|"fs", action?, scope?, type?, name?, paths? }`. A lista de Sessões e a página SessionDetail consultam `/api/run` (e escutam `run_status`) para marcar qualquer sessão sendo conduzida por uma execução em andamento com um indicador clicável **▶ Run** que leva de volta a `/run`.

### Importar histórico

**Configurações → Importar histórico** importa transcrições do Claude Code de `~/.claude/projects` e rollouts do Codex de `~/.codex/sessions` por leituras de pasta ou envios específicos de cada provedor. O Claude aceita os dois layouts oficiais de subagentes; o Codex reconhece `rollout-*.jsonl` recursivos ou JSONL com `session_meta`, mais títulos opcionais do `session_index.jsonl`.

## Eventos de hook

O painel processa estes tipos de hook do Claude Code:


| Tipo de hook        | Quando dispara                 | O que o painel faz                                                                           |
| ------------------- | ------------------------------ | -------------------------------------------------------------------------------------------- |
| `SessionStart`      | Uma sessão do Claude Code começa | Cria a sessão e o agente principal. Marca `awaiting_input_since` (com `awaiting_reason=session_start`) para uma sessão nova cair em **Aguardando** — exceto um SessionStart de origem `compact` (compactação automática no meio do turno), que deixa a marca como está para uma sessão trabalhando continuar **Ativa**. Reativa sessões retomadas. Abandona sessões órfãs sem atividade por `DASHBOARD_STALE_MINUTES` (padrão 180) |
| `UserPromptSubmit`  | O usuário aperta enter num prompt | Limpa a marca de espera e promove o agente principal a `working` — o único sinal de que turnos do assistente só com texto começaram, já que eles não emitem `PreToolUse` |
| `PreToolUse`        | O agente começa a usar uma ferramenta | Limpa a marca de espera, põe o agente em `working` e define `current_tool`. Se a ferramenta for `Agent`, cria um registro de subagente |
| `PostToolUse`       | A execução da ferramenta terminou | Limpa a marca de espera (cobre aprovações de permissão em que a Notification a marcou no meio da ferramenta). Limpa `current_tool`. O agente continua `working` |
| `Stop`              | O Claude termina de responder  | Sem erro: agente principal → `waiting` — o Claude terminou o turno, a vez é do usuário. `stop_reason=error`: marca o agente e a sessão como `error`. Subagentes em segundo plano continuam rodando |
| `SubagentStop`      | Um agente em segundo plano terminou | Encontra e conclui o subagente pela descrição, tipo ou tarefa. De propósito NÃO limpa a marca de espera — um subagente terminar não diz nada sobre o humano. **Dispara uma leitura do JSONL sem esperar resposta** (`scanAndImportSubagents`) que emite eventos `PreToolUse` + `PostToolUse` por ferramenta com o próprio `agent_id` do subagente, para a Linha do tempo mostrar toda ferramenta que o subagente rodou, não só o marcador de criação |
| `Notification`      | Notificação do agente          | Registra o evento. Mensagens de permissão/pedido de entrada põem o agente em `waiting` e marcam `awaiting_input_since` (com `awaiting_reason=notification`, reconhecidas por padrão: `permission`, `waiting for input`, `needs your approval`, …). Notificações de compactação viram eventos `Compaction`. Dispara uma notificação do navegador, se ativada |
| `SessionEnd`        | O processo da CLI do Claude Code sai | Remove a marca de espera. Se a sessão já estiver em `error`, o erro é preservado; senão marca todos os agentes e a sessão como `completed` |
| `Compaction`   | `/compact` detectado no JSONL  | Cria um subagente de compactação (tipo `compaction`) e um evento Compaction. Detectado pelas entradas `isCompactSummary` no JSONL da transcrição. Também detectado pela leitura periódica das sessões ativas |
| `APIError`     | Erro de API na transcrição JSONL | Extraído das entradas `isApiErrorMessage` (cota, limite de taxa, invalid_request) e de respostas brutas `type: "error"`. **Agora marca na hora a sessão e o agente como `error`** — antes era registrado como evento sem mudar o status. Gravado como evento com os detalhes do erro |
| `TurnDuration` | Tempo do turno na transcrição JSONL | Extraído de mensagens `system` do subtipo `turn_duration` com `durationMs`. Gravado como evento para análise de tempo por turno |
| `ToolError`    | Erro no resultado de ferramenta no JSONL | Extraído das entradas `toolUseResult.is_error`. Acompanha falhas por ferramenta para a análise de propagação de erros |
| `RemoteToolEvent` | Chamada de ferramenta enviada por uma máquina remota | Gravado por `POST /api/hooks/ingest-batch` para cada item de `tool_events[]` que uma máquina em trânsito/atrás de NAT envia. Deduplicado por `(session_id, event_type, uuid)` contra as linhas já gravadas e dentro do lote, então reenviar um lote é seguro |
| `RemoteTurn`   | Duração de turno enviada por uma máquina remota | Gravado por `POST /api/hooks/ingest-batch` para cada item de `turns[]`, com o `duration_ms` daquele turno. Mesma deduplicação por `(session_id, event_type, uuid)` do `RemoteToolEvent` |
| `Interrupted`  | Turno cancelado pelo usuário (Esc) | Sintetizado pelo vigia — o `Esc` não dispara hook, então uma sessão presa em `working` é detectada pelo marcador `[Request interrupted by user]` da transcrição ou, quando o Esc veio antes de qualquer saída, pelo tempo limite de ociosidade trabalhando (`DASHBOARD_WORKING_IDLE_SECONDS`). A sessão vai para **Aguardando** (igual a um `Stop` normal) |

## Notificações do navegador

O painel suporta notificações persistentes do navegador via Web Push (VAPID) para alertas em tempo real mesmo quando a aba do painel não está em foco ou o navegador está em segundo plano.

### Como funciona

1. **Ative** as notificações na página de Configurações pelo botão principal
2. **Conceda** a permissão do navegador quando pedida — isso registra um Service Worker e cria uma assinatura de push
3. **Configure** quais eventos disparam notificações:

| Evento                       | Padrão  | Descrição                                                       |
| ---------------------------- | ------- | --------------------------------------------------------------- |
| Nova sessão começa           | Ligado  | Dispara quando uma nova sessão do Claude Code é criada          |
| O Claude terminou de responder | Desligado | Dispara em eventos `Stop`, quando o Claude termina um turno de resposta |
| Sessão encerrada             | Desligado | Dispara no `SessionEnd`, quando o processo da CLI sai           |
| Sessão dá erro               | Ligado  | Dispara quando uma sessão termina com erro                      |
| Subagente criado             | Desligado | Dispara quando um subagente em segundo plano é criado           |

Além disso, qualquer evento de hook `Notification` do Claude Code dispara uma notificação do navegador, independentemente das opções por evento (desde que o botão principal esteja ligado).

### Arquitetura das notificações

- **Fluxo VAPID:** usa `web-push` no servidor para entregar as mensagens com segurança. As chaves VAPID são geradas automaticamente e guardadas em `data/vapid-keys.json`.
- **Service Worker:** um worker dedicado (`client/public/sw.js`) trata os eventos `push` que chegam e mostra as notificações com `silent: false` para garantir o som no macOS.
- **Assinaturas:** os endpoints de cada navegador ficam na tabela `push_subscriptions` do SQLite.
- **Persistência:** as notificações chegam mesmo com o navegador fechado, porque o Service Worker roda em segundo plano.
- **Notificação de teste:** um botão nas Configurações permite conferir o fluxo VAPID e o som.

### PWA e suporte offline

O painel, a página inicial e a Wiki são PWAs instaláveis separados, com manifestos e service workers independentes.

| Superfície | Manifesto | Service Worker | Estratégia de cache |
| --- | --- | --- | --- |
| Painel (`client/`) | `client/public/manifest.json` | `client/public/sw.js` | `/assets/*` imutáveis são cache-first; navegações, o worker, o manifesto, os ícones e `/` são network-first com plano B. `/api/*`, `/ws` e o HMR do Vite nunca entram no cache; os handlers de push continuam ativos. O Express manda cabeçalhos imutáveis de um ano para os assets e cabeçalhos de revalidação para os arquivos da casca. O `controllerchange` recarrega uma vez numa atualização, nunca na primeira instalação. |
| Página inicial (raiz) | `manifest.json` | `sw.js` | Pré-carrega a casca, o favicon e a imagem OG. As capturas de tela entram no cache na primeira visualização; a navegação é network-first com plano B offline. |
| Wiki (`wiki/`) | `wiki/manifest.json` | `wiki/sw.js` | Pré-carrega o HTML, CSS, JS, manifesto e favicon. O HTML fica network-first; CSS e JS são cache-first, permitindo uso offline depois de uma visita. |

Todos os workers chamam `skipWaiting()`, removem caches antigos versionados ao ativar e atualizam de forma limpa quando a versão do cache muda. Cada arquivo HTML inclui os metadados de modo standalone do iOS; os manifestos e os ícones touch da Apple usam `favicon.svg` com `sizes="any"`.

## Aviso de atualização

O painel observa o próprio checkout do git e mostra uma janela sempre que o branch padrão oficial tem commits à frente do HEAD. **Ciente de branch e de fork:** se você tem um remoto `upstream` (a convenção padrão para forks), ele tem preferência sobre o `origin`; o `master`/`main`/`HEAD` do remoto escolhido é a referência de comparação. O `manual_command` se adapta à sua situação — `git pull --ff-only` só quando seu branch realmente segue a referência oficial, senão um `git fetch` (e um merge fast-forward no caso de fork), para o comando nunca mentir. O usuário recebe o comando exato para rodar num terminal — o servidor **nunca** faz pull nem se reinicia sozinho, o que mantém o mecanismo portável entre sessões de desenvolvimento, supervisão por pm2/systemd/launchd/Docker e implantações remotas.

<p align="center">
  <a href="images/update.png"><img src="images/readme/update.png" alt="Janela de atualização do painel com comando para copiar" width="100%"></a>
</p>

### Como funciona

```mermaid
flowchart LR
    S["Início do servidor"] --> SCHED["Agendador de atualização<br/>consulta a cada 5 min"]
    SCHED --> PICK["Escolhe o remoto oficial<br/>upstream e depois origin"]
    PICK --> FETCH["git fetch remote prune<br/>execFile com limite de 120s"]
    FETCH --> CMP["rev-list HEAD vs<br/>remote master main HEAD"]
    CMP --> FP["A impressão digital mudou?"]
    FP -->|sim| WS["broadcast<br/>update_status"]
    FP -->|não| IDLE["pula o broadcast"]
    WS --> CLIENT["UpdateNotifier<br/>+ selo na barra lateral"]

    CHECK["POST updates check"] --> FETCH
    STATUS["GET updates status"] -.-> CMP

    style WS fill:#6366f1,stroke:#818cf8,color:#fff
    style CLIENT fill:#10b981,stroke:#34d399,color:#fff
```

Uma checagem é barata (`git fetch <remote> --prune` contra o remoto oficial — `upstream` se configurado, senão `origin`), envolvida em `execFile` (sem shell) com limite de 120s. As falhas — rede offline, instalação fora do git, nenhum remoto configurado, referência upstream que não se resolve — devolvem **payloads suaves** (ex.: `fetch_error: "..."`) em vez de lançar erro, então um remoto instável nunca trava o painel.

### Onde aparece na interface

| Superfície | Comportamento |
| --- | --- |
| **Janela** (`client/src/components/UpdateNotifier.tsx`) | Abre para um novo `remote_sha` disponível; mostra os commits de atraso, a referência seguida, uma nota opcional de branch/fork, o comando exato e os botões **Copiar comando**, **Verificar agora** e **Dispensar**. Esc ou clicar no fundo dispensa. A dispensa fica guardada no `localStorage` por SHA, então um SHA mais novo abre de novo. |
| **Botão da barra lateral** (`client/src/components/Sidebar.tsx`) | Sempre visível. Verde significa atrás; âmbar significa falha no fetch. Clicar limpa a dispensa e chama `POST /api/updates/check`. |
| **Terminal do servidor** | Imprime um comando emoldurado quando o status muda de atualizado para atrás, inclusive para quem usa sem interface. |

### API

| Endpoint | Para que serve |
| --- | --- |
| `GET /api/updates/status` | Checagem só leitura: roda `git fetch` contra o remoto oficial, compara o HEAD com o branch padrão dele e devolve o payload. |
| `POST /api/updates/check` | A mesma checagem, mas também transmite `update_status` pelo WebSocket para todos os clientes conectados atualizarem de uma vez. |

Os dois endpoints devolvem o mesmo formato de payload:

```json
{
  "git_repo": true,
  "update_available": true,
  "repo_root": "/Users/you/Claude-Code-Agent-Monitor",
  "remote_ref": "upstream/master",
  "canonical_remote": "upstream",
  "current_branch": "master",
  "tracking_upstream": "origin/master",
  "tracks_canonical": false,
  "situation": "fork_or_diverged_tracking",
  "local_sha": "abc1234...",
  "remote_sha": "def5678...",
  "commits_behind": 3,
  "manual_command": "cd \"/...\" && git fetch upstream && git merge --ff-only upstream/master && npm run setup",
  "situation_note": "You're on 'master' tracking 'origin/master'. This command fast-forwards your branch from upstream/master (the canonical default).",
  "message": "3 commit(s) on upstream/master not in your checkout."
}
```

`situation` é um destes: `tracking_canonical` (clone típico no branch padrão — `git pull --ff-only` funciona), `fork_or_diverged_tracking` (o nome do branch local bate com o oficial, mas segue outro remoto — `git fetch <remote> && git merge --ff-only <ref>`), `feature_branch` (fora do branch padrão — só fetch, a integração fica com o usuário) ou `detached_head`.

### O que **não** está aqui de propósito

Não existe `POST /api/updates/apply` nem auxiliar de autorreinício, por decisão de projeto. Um processo se atualizar de dentro de si mesmo não é confiável sem um supervisor externo — `npm run dev` (concurrently), `npm start`, `pm2`, `systemd`, `launchd` e Docker precisam cada um de uma lógica de reinício diferente, e falhas de `git pull` / `npm install` num servidor morrendo não têm caminho limpo de volta. Só detectar mantém o comportamento previsível em todo supervisor, todo sistema operacional e todo estado de branch, e ainda fecha a lacuna de "quando eu preciso dar pull?"; o usuário cuida da atualização em si no próprio shell.

### Configuração

| Variável de ambiente | Padrão | Observações |
| --- | --- | --- |
| `DASHBOARD_UPDATE_CHECK` | ligado | Defina `0` / `false` / `off` para desligar o agendador por completo. |
| `DASHBOARD_UPDATE_CHECK_INTERVAL_MS` | `300000` (5 min) | Intervalo entre as checagens automáticas. O mínimo é 60 000 ms — valores menores são ajustados. |

O Tabby mostra sozinho frases curtas em eventos importantes (sessão começou/terminou, erros, execução concluída). Abra o painel clicando no gato ou apertando **⌘B / Ctrl+B** (Esc fecha). Ele mostra:

- Uma **linha de status** ao vivo — `N ao vivo · M com erro · estado da conexão`.
- **Ações rápidas** — ir para Executar o Claude, Atividade, Sessões ou sessões com erro; silenciar os balões; limpar alertas.
- Uma caixa **Perguntar** (veja abaixo).

### Caixa Perguntar → repasse para Executar o Claude

A caixa **Perguntar** responde perguntas simples de status localmente, com os dados em cache — por exemplo "o que está rodando", "algum erro" ou "status". Qualquer outra pergunta é repassada para a página **Executar o Claude** que já existe (com um link direto para `/run?prompt=…`) para iniciar uma sessão real do Claude Code. O Tabby nunca chama um LLM sozinho; ele só reaproveita a página Executar o Claude para tudo que vai além de uma consulta rápida de status.

### Acessibilidade e degradação segura

O Tabby funciona pelo teclado, usa `aria-live` nos balões e respeita `prefers-reduced-motion`. Se o WebSocket cair, ele passa com segurança para um estado calmo `disconnected` em vez de dar erro. Dá para ligar ou desligar o Tabby em **Configurações** (traduzido em inglês, chinês, vietnamita, coreano, espanhol e português do Brasil), e a implementação fica em `client/src/components/Tabby/`.

## Sinais sonoros

O painel dá um **retorno sonoro discreto** da atividade das sessões ao vivo, então você pode deixá-lo num segundo monitor e ainda ouvir quando uma execução termina ou falha. O som vem **ligado por padrão** e pode ser desligado por completo com um clique.

### Síntese sem dependências

Não há assets `.mp3` ou `.wav` em lugar nenhum do repositório nem biblioteca de áudio no `package.json`. Cada sinal é gerado na hora com a **Web Audio API**: uma lista curta de osciladores (seno ou triângulo), cada um com o próprio envelope de ganho exponencial, mixados por um nó de ganho principal e um filtro passa-baixa, para o resultado ficar ao fundo do seu trabalho em vez de cortar através dele. O motor inteiro é um arquivo só, `client/src/lib/sound.ts`.

### Os sinais

| Sinal | Quando toca | Como soa |
| --- | --- | --- |
| `sessionStart` | Uma nova sessão aparece | Quinta justa subindo (C5 → G5) |
| `sessionComplete` | Uma sessão termina de responder (`Stop`) ou fecha (`SessionEnd`) | Arpejo maior resolvendo (E5 → G5 → C6) |
| `sessionError` | Uma sessão entra no estado `error` | Terça menor descendo suave numa onda triangular — perceptível, sem assustar |
| `subagentSpawn` | Um subagente é criado | Um dedilhado curto |
| `notification` | O Claude Code emite um evento `Notification` | Um par levemente desafinado soando como um sininho |
| `connected` / `disconnected` | O WebSocket do painel volta ou cai | Duas notas subindo / descendo |
| `click` | Você aperta um botão, link, aba ou chave | Um tique quase inaudível |

Os sinais ficam num conjunto em dó maior, então caudas sobrepostas nunca soam dissonantes, e todo envelope decai de forma exponencial em vez de cortar, o que evita o estalo de uma parada brusca.

### Sem atrapalhar

Três proteções impedem o áudio de virar barulho:

- **Intervalo por sinal** — o mesmo sinal não se repete em ~350 ms (45 ms para o tique de interação).
- **Orçamento global de rajadas** — no máximo 4 sinais começam em qualquer janela de 1,2 s, então importar histórico ou reconectar depois de uma queda nunca transforma uma enxurrada de mensagens do WebSocket numa enxurrada de bipes.
- **Política de autoplay** — nada toca antes da sua primeira interação de mouse, tecla ou toque com a página, pelas regras do navegador. Sinais antes disso são descartados em silêncio, não enfileirados.

Se o navegador não tiver suporte nenhum a Web Audio, toda chamada vira uma operação vazia segura — o painel só fica em silêncio.

### Configurações

**Configurações → Som** tem um botão principal, um controle de volume e uma chave para cada sinal. Ligar uma chave toca aquele sinal na hora, para você ouvir exatamente o que acabou de ativar, e um botão **Testar som** toca o sinal de conclusão quando quiser. As preferências ficam no `localStorage` em `agent-monitor-sound` e valem na hora em todo o app — sem recarregar. O painel é traduzido em inglês, chinês, vietnamita, coreano, espanhol e português do Brasil.

Por padrão, início de sessão, sessão concluída, erro de sessão, notificações do Claude Code e o tique de interação vêm ligados; criação de subagentes e mudanças de conexão vêm desligadas (são os mais falantes). A implementação fica em `client/src/lib/sound.ts` (motor + preferências) e `client/src/hooks/useSoundCues.ts` (ligação com o barramento de eventos), montados uma vez em `client/src/App.tsx`.

Ao abrir, o app:

1. Escolhe uma porta livre — preferindo **4820**, depois **4821–4829** e, se todas estiverem ocupadas, uma porta alta aleatória.
2. Se um servidor do painel saudável já responde a `/api/health` na `4820` (ex.: você rodou `npm start` num terminal), ele **adota esse servidor** em vez de abrir a porta de novo — sem colisão de porta, sem disputa pelo SQLite. Um servidor adotado continua rodando depois que você fecha o app.
3. Senão, ele sobe o servidor embutido e, na **primeira subida de um servidor próprio**, instala automaticamente os hooks do Claude Code e inicia os serviços em segundo plano (agendador de atualização, `cc-watcher`, reconciliação de execuções órfãs). Quem só instala o DMG já recebe eventos com **zero configuração manual** — sem checkout, sem `npm run install-hooks`.
4. **(macOS)** Recupera o **`PATH` do shell de login** para o recurso **Executar o Claude** achar e iniciar a CLI `claude` — senão um app aberto pelo Finder/Dock herda só o `PATH` mínimo do launchd e não acharia CLIs em `~/.local/bin`, `/opt/homebrew/bin`, pastas de gerenciadores de versão etc. (No Windows o processo já herda o `PATH` do usuário.)
5. Abre a janela do painel — a menos que o app tenha sido aberto no login (no macOS pelos Itens de login; no Windows pela entrada marcada em `HKCU\…\Run`), caso em que ele fica só na bandeja.
6. Ao sair, desliga o servidor embutido com calma e **fecha o SQLite de forma limpa** (checkpoint do WAL).

### Recursos

- **Bandeja e janela:** clique esquerdo mostra/esconde a janela; clique direito oferece **Abrir o painel**, **Abrir no navegador**, **Reiniciar servidor**, **Mostrar logs**, **Abrir no login** e **Sair**. O macOS usa um glifo de bandeja modelo colorido pelo sistema; o Windows e a janela/barra de tarefas usam o ícone colorido do app, inclusive em execuções de desenvolvimento não empacotadas.
- **Menu nativo:** menus padrão do aplicativo e atalhos com `⌘` / `Ctrl`. Só o macOS mantém **File → Open Dashboard** (`⌘1`) enquanto escondido; Windows/Linux reabrem de forma confiável pela bandeja.
- **Login e ciclo de vida:** o `SMAppService` registra os Itens de login do macOS; o Windows grava a entrada por usuário em `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Fechar esconde a janela enquanto a bandeja e o servidor continuam; abrir uma segunda vez foca a instância única que já existe.
- **Dados duráveis:** o SQLite e as chaves VAPID ficam fora do pacote, em `~/Library/Application Support/Claude Code Monitor/data/` ou `%APPDATA%\Claude Code Monitor\data\`. Reinstalar, atualizar e a desinstalação NSIS padrão preservam o histórico importado.
- **CLI e logs:** o macOS restaura o `PATH` do shell de login para aberturas pelo Finder/Dock conseguirem rodar o `claude`; o Windows usa o `PATH` herdado do usuário. **Mostrar logs** abre `~/Library/Logs/Claude Code Monitor/desktop.log` ou `%APPDATA%\Claude Code Monitor\logs\desktop.log`.

### Como obter

**Opção A — baixar um instalador pronto (recomendado).** Em **[Releases → latest](https://github.com/hoangsonww/Claude-Code-Agent-Monitor/releases/latest)** (público, sem login no GitHub). O CI publica automaticamente uma nova release `vX.Y.Z` sempre que a versão no `package.json` muda no `master`, então esse link sempre entrega o build atual:

| Plataforma | Arquivo | Observações |
| --- | --- | --- |
| macOS (Apple Silicon) | `ClaudeCodeMonitor-<ver>-arm64.dmg` | arraste para `/Applications` |
| macOS (Intel) | `ClaudeCodeMonitor-<ver>-x64.dmg` | arraste para `/Applications` |
| Windows (instalador) | `ClaudeCodeMonitor-Setup-<ver>-x64.exe` | instalação por usuário, sem admin |
| Windows (portátil) | `ClaudeCodeMonitor-<ver>-x64-portable.exe` | roda sem instalar |

Builds novos por commit também ficam como artefatos do CI (exige login, guardados por 14 dias): `ClaudeCodeMonitor-dmg` do job `🍎 macOS Desktop (DMG)` e `ClaudeCodeMonitor-win` do job `🪟 Windows Desktop (EXE)` — úteis para testar o `master` antes da próxima tag de release.

**Opção B — compilar você mesmo.** Na raiz do repositório:

```bash
npm run setup                # install root + client deps, build client, install hooks
npm run build                # build the React client (client/dist)
npm run desktop:install      # install Electron + electron-builder into desktop/ (preflights native deps; prints setup help on failure)
npm run desktop:dmg:arm64    # macOS:   fast single-arch DMG → desktop/release/ClaudeCodeMonitor-<ver>-arm64.dmg
npm run desktop:win          # Windows: NSIS installer → desktop/release/ClaudeCodeMonitor-Setup-<ver>-x64.exe
```

> [!NOTE]
> **DMGs são gerados no macOS; os `.exe` do Windows, no Windows** — o electron-builder empacota para o sistema da máquina. O build `npm run desktop:dmg` do macOS empacota o app **duas vezes** (uma por arquitetura) e gera **os dois** DMGs por arquitetura (`arm64` + `x64`) — o build de release; ele não os junta num binário universal. Para o seu próprio Mac use o de uma arquitetura só, `desktop:dmg:arm64` / `desktop:dmg:x64`. No Windows, o `better-sqlite3` é baixado como binário pronto do Electron pelo `npm run desktop:install`, então no caso comum não precisa do toolchain C++ do Visual Studio. Se o build falhar (sem binário pronto, ou sem toolchain C++), o `desktop:install` mostra a correção exata para cada sistema mais uma alternativa sem toolchain e falha de forma clara, em vez de deixar uma instalação quebrada.

### Comandos de build

Todos os comandos rodam na **raiz do repositório**:

| Comando                     | O que faz                                                                    |
| --------------------------- | ---------------------------------------------------------------------------- |
| `npm run desktop:install`   | Instala o Electron + electron-builder em `desktop/`; recompila o `better-sqlite3` para a ABI do Electron; testa antes o build nativo do `better-sqlite3` e mostra ajuda prática de configuração (incl. uma alternativa sem toolchain) se falhar |
| `npm run desktop:build`     | Compila o código TypeScript do desktop em `desktop/out/`                      |
| `npm run desktop:dev`       | Compila e abre o app Electron para testar localmente                          |
| `npm run desktop:test`      | Roda o teste rápido (abre o Electron, testa `/api/health`, desliga)           |
| `npm run desktop:dmg`       | **macOS:** gera **os dois** DMGs (arm64 + x64) — o certo para release, **mais lento** (empacota cada arquitetura) |
| `npm run desktop:dmg:arm64` | **macOS:** gera um DMG só para Apple Silicon — **rápido** (~1 min), recomendado para o seu próprio Mac |
| `npm run desktop:dmg:x64`   | **macOS:** gera um DMG só para Intel — **rápido** (~1 min)                    |
| `npm run desktop:dmg:universal` | **macOS:** gera um único DMG **universal** combinado (arm64 + x86_64) — opcional, **o mais lento**, não é o que a release publica |
| `npm run desktop:win`       | **Windows:** gera o instalador NSIS `.exe` (x64)                              |
| `npm run desktop:win:portable` | **Windows:** gera o `.exe` portátil sem instalação (x64)                   |

O DMG gerado para macOS tem **~80 MB** (≈ 250 MB em disco depois de instalado) e o instalador do Windows é parecido — o custo padrão de um pacote Electron.

### Assinatura e notarização

O macOS usa assinatura ad-hoc por padrão e define `CSC_IDENTITY_AUTO_DISCOVERY=false`, então certificados locais nunca são escolhidos por acidente. A assinatura com Developer ID usa `CSC_LINK` mais `CSC_KEY_PASSWORD`; a notarização adiciona `APPLE_ID`, `APPLE_TEAM_ID` e `APPLE_APP_SPECIFIC_PASSWORD`. O Windows não tem assinatura por padrão e ativa o Authenticode pelas mesmas variáveis `CSC_LINK` e de senha. O CI ativa qualquer um dos caminhos quando as credenciais existem, sem mudar código.

### Notas de implementação

- **ABI nativa:** `desktop/` mantém um `better-sqlite3` compilado para o Electron e redireciona `server/db.js` para ele; a cópia da raiz continua compatível com o Node do sistema e com os testes do servidor. Depois de builds de DMG por arquitetura, o `prebuild` do desktop conserta a ABI local sozinho e falha cedo com ajuda de configuração se o binário estiver faltando.
- **Paridade do servidor:** a função exportada `startBackgroundServices()` dá ao servidor embutido o mesmo agendador de atualização, observador de configuração e reconciliação de órfãos de `node server/index.js`; o caminho standalone e os outros workspaces continuam com o mesmo comportamento.
- **CI e releases:** jobs de macOS e Windows filtrados por caminho fazem testes rápidos e enviam dois DMGs de uma arquitetura mais os EXEs NSIS e portátil. Mudanças de versão no `master` anexam todos os arquivos à `vX.Y.Z`; gere de novo `desktop/assets/icon.ico` com `npm run build:win-icon`.

Veja [`DESKTOP.md`](./DESKTOP.md) para instalação e uso no dia a dia, e [`desktop/README.md`](./desktop/README.md) para processo, ciclo de vida, portas e builds.

## Marketplace de plugins

O pacote contém **66 skills de plugin, 18 subagentes do Claude, 34 comandos do Claude, 3 auxiliares de CLI, 3 configurações de hook e 2 plugins com MCP**.

claude plugin marketplace add hoangsonww/Claude-Code-Agent-Monitor
claude plugin install ccam-platform@claude-code-agent-monitor-plugins

# Codex
codex plugin marketplace add hoangsonww/Claude-Code-Agent-Monitor
codex plugin add ccam-platform@claude-code-agent-monitor-plugins

# Open Agent Skills / skills.sh-compatible CLI
npx skills add hoangsonww/Claude-Code-Agent-Monitor --list

# Install one skill for Claude Code and Codex in the current project
npx skills add hoangsonww/Claude-Code-Agent-Monitor \
  --skill mcp-server \
  --agent claude-code \
  --agent codex \
  --yes

# Verify, update, and remove the project-scoped skill
npx skills list --json
npx skills update --project --yes
npx skills remove mcp-server --yes

# Add --global to install at user scope, then manage that scope explicitly
npx skills add hoangsonww/Claude-Code-Agent-Monitor \
  --skill mcp-server \
  --agent claude-code \
  --agent codex \
  --global \

### Implantação na nuvem

A pilha de `deployments/` funciona em qualquer serviço Kubernetes conforme, incluindo EKS, GKE, AKS, OKE e clusters próprios. O CCAM usa SQLite, então todo manifesto suportado exige **um único gravador ativo do painel por volume persistente**, com rollout Recreate. HPA, réplicas ativo-ativo, blue-green e canary ficam sem suporte de propósito enquanto o SQLite for o backend de persistência.

```mermaid
flowchart LR
  CI["CI: testar · validar · escanear · atestar · assinar"] --> HELM["Helm / Kustomize / Terraform"]
  HELM --> APP["Painel CCAM<br/>exatamente 1 réplica"]
  APP --> PVC[("PVC ReadWriteOnce retido")]
  EDGE["Ingress ou Gateway API<br/>TLS + WebSocket"] --> APP
  PROM["Prometheus Operator"] -->|"Bearer /api/metrics"| APP
  MCP["Sidecar MCP autenticado"] --> APP
```

- **Helm:** um só gravador garantido pelo schema, suporte a digest, PVC retido, Ingress ou Gateway API, montagem de token compatível com External Secrets, NetworkPolicy, MCP e ServiceMonitor opcionais.
- **Kustomize:** base com PSS restrito mais overlays de dev/staging/produção e componentes opcionais de MCP, monitoramento, Gateway API e snapshots CSI.
- **Terraform:** implanta o chart Helm validado num cluster Kubernetes existente. Rede da nuvem, identidade do cluster, CSI, TLS e sincronização de segredos continuam com o provedor.
- **Operação:** backup online consistente do SQLite com SHA-256, restauração verificada com scale-to-zero, implantação/rollback/remoção com backup antes e checagens de saúde autenticadas.
- **Cadeia de suprimentos no CI:** as imagens do app e do MCP são escaneadas, publicadas para amd64/arm64 com SBOM e procedência SLSA e assinadas sem chave com o Cosign.

## Solução de problemas

| Problema                          | Solução                                                                                                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `better-sqlite3` não instala      | Não é grave — o servidor passa sozinho para o `node:sqlite` embutido no Node.js (Node 22+). Em versões mais antigas do Node, instale o Python 3 e as ferramentas de build C++ e depois rode `npm rebuild better-sqlite3` |
| Os hooks não disparam             | Rode `npm run install-hooks` e reinicie o Claude Code. Confira se os hooks existem em `~/.claude/settings.json`                                                  |
| O painel não mostra dados         | Garanta que o servidor esteja rodando (`npm run dev`) antes de iniciar uma sessão do Claude Code. Confira `http://localhost:4820/api/health`                     |
| WebSocket desconectado            | O client reconecta sozinho a cada 2 segundos. Confira se a porta 4820 não está bloqueada por um firewall                                                         |
| Dados antigos depois de reiniciar | O banco persiste entre reinícios. Rode `npm run seed` para dados de demonstração novos, ou apague `data/dashboard.db` para zerar                                  |
| As ferramentas MCP não conectam   | Confirme que a API do painel está no ar em `MCP_DASHBOARD_BASE_URL` e recompile/inicie o MCP (`npm run mcp:build`, `npm run mcp:start`)                          |
