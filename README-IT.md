# Dashboard degli agenti per Claude Code & Codex

### Piattaforma di monitoraggio in tempo reale per l'attività degli agenti Claude Code & Codex 🚀

Una dashboard professionale per tracciare e visualizzare in tempo reale le sessioni degli agenti Claude Code e Codex, l'uso degli strumenti e l'orchestrazione dei subagenti. Costruita con Node.js, Express, React e SQLite, si integra direttamente con Claude Code e Codex tramite i loro sistemi di hook nativi per un tracciamento e un'analisi delle sessioni senza interruzioni.

## Panoramica

Traccia le sessioni, monitora gli agenti in tempo reale, visualizza l'uso degli strumenti e osserva l'orchestrazione dei subagenti attraverso un'interfaccia web professionale a tema scuro. Si integra direttamente con Claude Code e Codex tramite i loro sistemi di hook nativi.

```mermaid
graph LR
    A["Claude Code<br/>Session"] -->|hooks fire on<br/>tool use / stop| B["Hook Handler<br/>(Node.js script)"]
    B -->|HTTP POST| C["Dashboard Server<br/>(Express + SQLite)"]
    C -->|WebSocket<br/>broadcast| D["Dashboard UI<br/>(React + Tailwind)"]
    style A fill:#6366f1,stroke:#818cf8,color:#fff
    style B fill:#1a1a28,stroke:#2a2a3d,color:#e4e4ed
    style C fill:#1a1a28,stroke:#2a2a3d,color:#e4e4ed
    style D fill:#10b981,stroke:#34d399,color:#fff
```

Oltre alla dashboard di monitoraggio in tempo reale, include anche un'implementazione locale di server MCP in `mcp/` che espone un catalogo di strumenti per l'introspezione e la gestione della dashboard stessa, rendendo facile integrare le operazioni della dashboard direttamente nei tuoi workflow di Claude Code e Codex. C'è anche un livello di estensioni per gli agenti, che fornisce plugin, skill e subagenti di Claude Code e Codex per l'interazione con la dashboard, l'analisi e l'intelligenza dei workflow.

### Internazionalizzazione (i18n)

La UI include di serie il cambio di lingua integrato per inglese (`en`), cinese (`zh`), vietnamita (`vi`), coreano (`ko`), spagnolo (`es`) e italiano (`it`). Un menu a tendina personalizzato per la lingua evita che il selettore affolli la sidebar man mano che vengono aggiunte nuove lingue. Le risorse linguistiche sono caricate per namespace e persistite nello storage del browser per mantenere stabile la preferenza dell'utente tra i refresh.

```mermaid
flowchart LR
    A["User selects language<br/>en / zh / vi / ko / es / it"] --> B["i18next detector<br/>localStorage -> navigator"]
    B --> C["Resolved language<br/>fallback: en"]
    C --> D["Namespace resources<br/>common/nav/dashboard/..."]
    D --> E["React useTranslation hooks"]
    E --> F["Localized UI + accessibility labels"]
```

Per l'architettura completa e le indicazioni operative, consulta [docs/I18N.md](./docs/I18N.md).

> **Confini di sicurezza locali:** Run Agent accetta qualsiasi directory di lavoro assoluta esistente e la canonicalizza prima dell'uso, così gli avvii dalla home e dai progetti recenti restano supportati. I provider di webhook hosted richiedono HTTPS; i target generici e n8n possono usare HTTP per ricevitori locali/self-hosted, e la consegna non segue mai i redirect.

## Come funziona

La dashboard si integra con Claude Code tramite il suo sistema di hook nativo per fornire un monitoraggio in tempo reale dell'attività degli agenti. Ecco una panoramica dell'architettura e del flusso dei dati:

```mermaid
sequenceDiagram
    participant CC as Claude Code
    participant HH as Hook Handler
    participant API as Express Server
    participant DB as SQLite
    participant WS as WebSocket
    participant UI as React Client

    CC->>HH: stdin (JSON event)
    HH->>API: POST /api/hooks/event
    API->>DB: Insert/update records
    API->>WS: Broadcast update
    WS->>UI: Push message
    UI->>UI: Re-render component

    Note over CC,HH: Hooks fire on SessionStart,<br/>PreToolUse, PostToolUse,<br/>Stop, SubagentStop,<br/>SessionEnd, Notification.<br/>Compaction detected from JSONL
    Note over API,DB: Transactional writes<br/>with auto session/agent creation
    Note over WS,UI: ~0ms latency,<br/>no polling
```

> [!IMPORTANT]
> Vedi [ARCHITECTURE.md](./ARCHITECTURE.md) per un approfondimento sull'architettura del server, lo schema del database, le route API, il design del WebSocket, il routing del client, il flusso del gestore degli hook, le modalità di deployment e i diagrammi dettagliati del ciclo di vita di sessioni e agenti.

### Ciclo di vita degli hook

1. **Claude Code** fa scattare un hook all'avvio della sessione, all'uso di uno strumento, alla fine del turno, al completamento di un subagente e all'uscita dalla sessione
2. Il **gestore degli hook** (`scripts/hook-handler.js`) legge l'evento JSON dallo stdin, risolve le dashboard live via `~/.claude/.agent-dashboard.json` (o `CLAUDE_DASHBOARD_PORT` se impostata) e fa il POST dello stesso payload verso **un target di ingest per ogni directory dati SQLite unica** (vince la porta più bassa quando Docker e `npm run dev` condividono `~/.claude/agent-dashboard`, così gli eventi non vengono mai ingeriti due volte). I server con database **diversi** (es. l'app desktop che usa la propria directory Application Support accanto a `npm run dev`) ricevono comunque ciascuno gli hook. Fallisce silenziosamente con un timeout di sicurezza di 5 s così non blocca mai Claude Code, e le promise per target non vanno mai in reject così un singolo listener morto non può affamare gli altri.
3. Il **server** elabora l'evento dentro una transazione SQLite:
   - Auto-crea sessioni e agenti principali al primo contatto
   - Rileva le chiamate allo strumento `Agent` per tracciare la creazione dei subagenti
   - Al `SessionStart`, marca `awaiting_input_since` della sessione e dell'agente principale così una CLI appena aperta ferma al prompt atterra subito in **Waiting**
   - Al `UserPromptSubmit` (l'utente preme invio), cancella il flag di attesa e promuove l'agente principale a `working` — l'unico segnale affidabile che un turno dell'assistente di solo testo è iniziato, dato che non emette `PreToolUse`
   - Imposta l'agente a "working" al `PreToolUse` (cancellando anche il flag di attesa), lo mantiene working attraverso il `PostToolUse`
   - Allo `Stop` (Claude finisce di rispondere), l'agente principale va in "waiting" — Claude ha finito il suo turno, la palla è all'utente. I subagenti in background continuano a girare. La sessione resta `active`. Uno Stop con `stop_reason=error` marca l'agente `error` e la sessione `error`
   - A una `Notification` di permesso (riconosciuta dal pattern del messaggio: `permission`, `waiting for input`, `needs your approval`, …), imposta l'agente a `waiting` e marca `awaiting_input_since`
   - `SubagentStop` deliberatamente NON cancella il flag di attesa (un subagente in background che finisce non ci dice nulla sull'umano)
   - Marca i subagenti come completati individualmente via `SubagentStop`. Dopo il ritorno di `res.json()`, lancia un passaggio fire-and-forget `scanAndImportSubagents` che percorre i file `subagents/agent-*.jsonl` della sessione, accoppia i blocchi `tool_use` ↔ `tool_result` per `tool_use_id` ed emette eventi `PreToolUse` + `PostToolUse` sotto l'`agent_id` proprio di ciascun subagente — chiudendo il gap per cui le chiamate agli strumenti interne ai subagenti sarebbero altrimenti invisibili alla dashboard
   - Al `SessionEnd` (il processo CLI esce), rimuove il flag di attesa. Se la sessione è in `error`, lo stato di errore viene preservato; altrimenti marca tutti gli agenti + la sessione come `completed`
   - Al `SessionStart`, qualsiasi altra sessione attiva senza attività per `DASHBOARD_STALE_MINUTES` (default 180 = 3 h, sovrascrivibile via env) viene automaticamente marcata "abandoned" con i suoi agenti completati. Questo gestisce `/resume` dentro una sessione, Ctrl+C e altri scenari in cui una sessione resta orfana senza un `SessionEnd` pulito
   - Riattiva le sessioni completed/error/abandoned quando arrivano nuovi eventi di lavoro (sessione ripresa). Anche gli eventi Stop e SubagentStop riattivano le sessioni completed/abandoned — questo gestisce le sessioni preesistenti importate prima dell'avvio del server, dove il primo evento hook può essere uno Stop
   - **Recupero dagli errori**: solo `UserPromptSubmit` e `PreToolUse` possono recuperare una sessione da `error` a `active` — a indicare che l'utente ha riprovato attivamente
   - Rileva la compattazione delle conversazioni (voci `isCompactSummary` nella trascrizione JSONL) e crea agenti + eventi `Compaction`. Le baseline dei token sono preservate attraverso le compattazioni così nessun uso va perso. Le letture delle trascrizioni usano una cache condivisa basata su stat con letture incrementali per offset di byte — vengono analizzati solo i nuovi byte aggiunti dall'ultima lettura, con uno speedup di ~50x per le sessioni lunghe
   - Estrae gli errori API (voci `isApiErrorMessage`: limiti di quota, rate limit, invalid_request) e le risposte grezze `type: "error"` dalle trascrizioni JSONL, salvati come eventi `APIError`. Le durate dei turni (`system` con sottotipo `turn_duration`) sono salvate come eventi `TurnDuration`. Gli errori dei risultati degli strumenti (`toolUseResult.is_error`) sono tracciati come eventi `ToolError`
   - **Watchdog di rilevamento errori** — un timer in background gira ogni 15 secondi, scansionando le sessioni attive senza eventi hook recenti (>10 s di stallo). Rilegge i loro file di trascrizione cercando errori API (fallimenti di autenticazione, rate limit, esaurimento della quota), deriva i percorsi delle trascrizioni dalla `cwd` della sessione per le sessioni importate senza `transcript_path` nei dati degli eventi, e marca sessioni/agenti come `error` quando trova errori API. Questo intercetta i casi in cui la CLI di Claude non fa scattare un hook dopo un errore API (es. errori di autenticazione 401 dove la CLI mostra l'errore e aspetta)
   - **Recupero dall'interruzione utente (Esc)** — annullare un turno con `Esc` non fa scattare **alcun hook** (una limitazione documentata di Claude Code), quindi senza intervento l'agente principale resterebbe bloccato in `working` per sempre. Lo stesso watchdog da 15 s recupera in due modi: (1) quando l'annullamento lascia un marcatore `[Request interrupted by user]` nella trascrizione (Esc *dopo* un po' di output), la cache delle trascrizioni lo segnala via `pendingInterrupt` — derivato puramente dall'ordinamento della trascrizione (ultima interruzione vs ultima attività reale del turno, stesso orologio, quindi funziona anche per un annullamento sotto il secondo) — e la sessione passa a **Waiting** entro ~15 s; (2) quando Esc viene premuto *prima di qualsiasi output*, Claude Code non scrive alcun marcatore, quindi si applica un fallback a timeout di inattività — se l'agente principale è stato `working` **senza strumenti in volo** e **né un evento hook né la trascrizione sono avanzati** per `DASHBOARD_WORKING_IDLE_SECONDS` (default `120`), il turno viene considerato morto e la sessione passa a **Waiting**. Entrambi i percorsi registrano un evento `Interrupted` e portano la sessione nello stesso stato Waiting che produce uno `Stop` normale. L'output in streaming (trascrizione ancora in crescita) e le chiamate agli strumenti in volo (`current_tool` impostato) sono esenti; un raro flip errato si auto-ripara al successivo hook reale
   - **Reap di liveness delle sessioni morte** — uscire da Claude Code (Ctrl+C, chiusura del terminale) fa scattare un hook `SessionEnd`, ma se la dashboard non è in esecuzione in quel momento l'evento è perso per sempre e la sessione resterebbe in **Waiting** fino allo sweep di stallo (3 h per default). Lo stesso watchdog da 15 s chiude il gap con un **probe di liveness dei processi**: elenca i processi CLI `claude` in esecuzione (`ps` + `lsof` su macOS, `/proc` su Linux) e completa qualsiasi sessione `active` la cui `cwd` non ha un processo claude vivo — portandola nello stesso stato `completed` che produce un vero `SessionEnd`, con un evento `SessionEnd` sintetico sulla timeline. Guardie: nei tick del watchdog la trascrizione della sessione non deve essere stata scritta per almeno `DASHBOARD_LIVENESS_IDLE_SECONDS` (default `60`; l'ultima scrittura di hook è l'orologio di fallback quando nessuna trascrizione esiste su disco) — i **passaggi di boot saltano interamente questo gate**, così una sessione chiusa anche un secondo prima del lancio viene ripulita immediatamente — e il probe risponde "nessuna risposta" (senza cambiare nulla) su Windows, dentro i container (i processi host lì sono invisibili), quando `ps`/`lsof` falliscono, o quando esplicitamente disabilitato via `DASHBOARD_LIVENESS_PROBE=0`. In un deployment **misto** il reap salta automaticamente anche qualsiasi sessione la cui `cwd` non è POSIX-assoluta — una sessione inoltrata da un'altra macchina via hook domestici riporta il percorso proprio dell'origine (es. un `D:\Git\ai-deck` Windows) che una scansione locale `ps`/`lsof`/`/proc` non può mai matchare, così le sessioni remote sono protette senza disabilitare il probe per quelle genuinamente locali. Anche le **sessioni da Sorgenti dati remote** (`sessions.source` ≠ `local`) vengono sempre saltate — la loro `cwd` è legittimamente POSIX-assoluta su un'altra macchina, quindi il probe dei processi locale non dice nulla su di loro; il loro ciclo di vita è interamente di proprietà della riconciliazione remote-sync descritta sopra. Un completamento errato si auto-ripara: il successivo evento hook riattiva la sessione. Oltre alla cadenza del watchdog da 15 s, il reap gira **immediatamente all'avvio** (ripulendo le sessioni morte già nel DB da un'esecuzione precedente prima ancora che vengano renderizzate) e **di nuovo ~5 s dopo** (coprendo le sessioni appena importate dalla sincronizzazione di avvio), così una sessione morta mentre la dashboard era giù non appare mai come Waiting
   - Uno sweep periodico del server intercetta le sessioni abbandonate e le nuove compattazioni sfuggite al rilevamento basato sugli eventi (es. `/compact` non fa scattare hook, `/resume` a pochi secondi dalla creazione della sessione). La cadenza è derivata da `DASHBOARD_STALE_MINUTES` (¼ della soglia, limitata tra 60 s e 5 min). Lo sweep legge `transcript_path` direttamente dalla riga di ogni sessione attiva (un piccolo lookup su indice) invece di scansionare la tabella degli eventi; la colonna è popolata dal gestore degli hook la prima volta che vede un percorso di trascrizione ed è backfillata una tantum dagli eventi esistenti dalla migrazione di `db.js`, con un indice parziale `idx_sessions_active_tp` che copre esattamente le righe lette dallo sweep. Lo sweep condivide la cache delle trascrizioni con il gestore degli hook, evitando I/O duplicato. La pulizia delle sessioni abbandonate evice anche la voce della cache delle trascrizioni per limitare la memoria. Le sessioni da **Sorgenti dati remote** (`source` ≠ `local`) restano di proprietà del mirror solo finché il loro provider Claude Code o Codex corrispondente è in salute; se quel provider è indisponibile, in errore o incagliato in `syncing`, la pulizia periodica e di avvio usano la normale regola di stallo così una vecchia card Waiting non può persistere per sempre
   - La **sincronizzazione continua dei progetti** (`startSessionSync`) mantiene `~/.claude/projects` scopribile oltre il backfill di avvio una tantum protetto da marker: un progetto aggiunto in seguito le cui sessioni non passano mai per gli hook resterebbe altrimenti invisibile fino a una scansione manuale. Uno sweep immediato all'avvio, un `fs.watch` con debounce (ricorsivo su macOS/Windows; root + figli immediati su Linux) e un poll `DASHBOARD_SESSION_SYNC_MS` (default 30 s; `0` disabilita il poll, il watcher resta) condividono una sola cache di mtime e uno sweep coalizzato che ri-analizza solo i file il cui mtime è avanzato — e salta una sessione già importata e invariata senza ri-analizzarla, così il costo di riavvio resta O(file nuovi/modificati). Ogni sessione appena scoperta o cresciuta trasmette `session_created`/`session_updated` più il suo agente principale, gli stessi frame emessi dagli hook
4. Il **WebSocket** trasmette il cambiamento a tutti i client connessi
5. La **UI** riceve l'aggiornamento e ri-renderizza i componenti interessati in tempo reale senza polling.

```mermaid
    GROUP --> MATCH{"Match model<br/>to pricing rule"}
    SORT --> MATCH
    MATCH --> CALC["cost = Σ (tokens / 1M) × rate<br/>for input, output, cache_read, cache_write"]
    CALC --> RESULT["{ total_cost, breakdown[] }"]
    style TU fill:#003B57,stroke:#005f8a,color:#fff
    style PR fill:#6366f1,stroke:#818cf8,color:#fff
    style RESULT fill:#10b981,stroke:#34d399,color:#fff
```

> [!IMPORTANT]
> Il flusso di calcolo dei costi si basa sull'uso dei token e sulle regole di pricing dei modelli. Assicurati che le tue regole di pricing siano aggiornate per riflettere costi accurati. Aggiorna la tabella di pricing dei modelli dalla pagina Impostazioni per mantenere un tracciamento dei costi accurato — la dashboard non recupera automaticamente aggiornamenti di prezzo da sorgenti esterne. Una volta impostate le regole di pricing, la dashboard le applica retroattivamente a tutte le sessioni per una rendicontazione dei costi coerente.

| `DASHBOARD_ALLOWED_HOSTS` | _(loopback)_ | Valori `Host` extra separati da virgola consentiti sugli upgrade HTTP + WebSocket (guardia contro il DNS-rebinding). Aggiungi qui i tuoi hostname LAN quando bindi oltre il loopback |

> **Sicuro per default.** Il server si binda a `127.0.0.1` e **non** è raggiungibile dalla rete out of the box ([GHSA-gr74-4xfh-6jw9](./.github/SECURITY.md)). Per esporlo su una LAN, imposta **sia** `DASHBOARD_HOST` (es. `0.0.0.0`) **sia** `DASHBOARD_TOKEN` (che allora protegge `/api/*` e il WebSocket), ed elenca i tuoi hostname LAN in `DASHBOARD_ALLOWED_HOSTS`. Vedi [`.env.example`](./.env.example) e [`.github/SECURITY.md`](./.github/SECURITY.md) per i dettagli.

Per i clone git, il server esegue periodicamente `git fetch` su `origin` e confronta il tuo checkout con `origin/master`, `origin/main` o `origin/HEAD`. Quando sei indietro, un messaggio appare nel terminale del server e una modale appare nella UI con il comando esatto da eseguire. La dashboard non fa mai pull né si riavvia da sola — copi il comando, lo esegui in un terminale, poi riavvii il server nello stesso modo in cui lo avevi avviato.

## CLI `ccam`

L'intera superficie di funzionalità della dashboard è disponibile anche da qualsiasi terminale tramite la CLI **`ccam`** senza dipendenze (`bin/ccam.js`). Viene linkata automaticamente da `npm run setup` (via `npm link`), dopo di che `ccam <command>` funziona da qualsiasi directory. Scopre la dashboard in esecuzione tramite `~/.claude/.agent-dashboard.json` (lo stesso registro dei server live usato dal gestore degli hook), con gli override d'ambiente `CLAUDE_DASHBOARD_PORT` / `DASHBOARD_PORT`, ripiegando su `http://127.0.0.1:4820`.

```bash
# Server
ccam status                       # indicatore ● running / ○ not running
ccam start [--port N]             # avvia il server in background (staccato)
ccam stop                         # ferma con grazia il server in background
ccam repl                         # shell interattiva (anche: shell, i)

# Monitoraggio
ccam health                       # la dashboard è su?
ccam stats                        # totali, eventi di oggi, distribuzioni di stato
ccam kanban                       # sessioni + agenti raggruppati per colonne di stato
ccam tail [--session <id>]        # feed live degli eventi nel terminale (Ctrl+C ferma)

# Dati
ccam sessions [--status s] [--q text] [--limit n]
ccam session <id>                 # dettaglio: albero degli agenti, costo, eventi recenti
ccam agents   [--status s] [--session id]
ccam events   [--session id] [--limit n]

# Insight
ccam analytics                    # totali dei token, strumenti principali, tipi di agente
ccam workflows [--session id]     # statistiche e pattern di intelligenza dei workflow
ccam runs [--session id]          # esecuzioni dinamiche dello strumento Workflow
ccam cost [--session <id>]        # costo stimato totale con ripartizione per modello
                                  # (--session limita a una; mostra i sovrapprezzi degli strumenti;
                                  #  avvisa sui modelli con uso ma senza regola di pricing)

# Alert e webhook
ccam alerts [--unacked]           # feed degli alert scattati
ccam alerts ack <id> | ack-all    # riconosci gli alert
ccam rules                        # elenca le regole di alert
ccam webhooks                     # elenca i target webhook
ccam webhooks test <id>           # invia un alert di test sintetico

# Pricing
ccam pricing                      # elenca le regole di pricing dei modelli (incl. colonne fast-mode e intro)
ccam pricing set <pattern> --input N --output N [--cache-read N --cache-write N]
                 [--cache-write-1h N] [--fast-input N --fast-output N]
                 [--intro-input N --intro-output N … --intro-until YYYY-MM-DD]
ccam pricing delete <pattern>
ccam pricing reset

# Import
ccam import rescan                # ri-scansiona ~/.claude/projects
ccam import path <dir>            # importa ogni .jsonl sotto una directory

# Amministrazione
ccam doctor                       # diagnosi di connettività, hook e database
ccam info                         # JSON grezzo delle informazioni di sistema
ccam export [file.json]           # export completo dei dati in JSON
ccam import-data <file.json>      # ripristina un export (idempotente, non distruttivo)
ccam cleanup --hours N --days M   # abbandona sessioni stantie / elimina quelle vecchie
ccam reinstall-hooks              # reinstalla gli hook di Claude Code
ccam update-check                 # il checkout è indietro rispetto all'upstream? (stampa il comando di aggiornamento)
ccam clear-data --yes             # elimina TUTTI i dati (richiede --yes)
ccam open                         # apre la dashboard nel browser
ccam version                      # stampa la versione della CLI (anche --version / -v)
```

I comandi basati sull'API richiedono il server in esecuzione — quando non lo è, **i comandi di sola lettura ripiegano sulla lettura diretta di `data/dashboard.db`** (con un banner esplicito `⚠ Offline mode`, e le sessioni `active` salvate-ma-morte corrette in visualizzazione dallo stesso probe di liveness dei processi usato dal watchdog del server), mentre i comandi che non possono girare correttamente senza il server (`tail` live, calcoli di analytics/costi, mutazioni) stampano l'indicatore `○ Dashboard server is NOT running` con la ragione specifica e i comandi di avvio; `ccam start` tira su un server di produzione in background. I comandi di lettura sono sempre sicuri; l'unico comando distruttivo (`clear-data`) rifiuta di girare senza un `--yes` esplicito. L'output è una vera UI da terminale — tabelle con bordi disegnati e colonne numeriche allineate a destra, icone di stato (`● active`, `○ waiting`, `✔ completed`, `✖ error`), grafici a barre inline per stats/analytics/cost e veri alberi degli agenti `├─`/`└─` — con colori ANSI auto-abilitati su un TTY, spenti quando l'output è in pipe, e controllabili via `--no-color` / `NO_COLOR` / `FORCE_COLOR`. Per una sessione di monitoraggio live, **`ccam repl`** (alias `shell` / `i`) apre una shell interattiva dove digiti i comandi senza il prefisso `ccam` — con un banner di benvenuto CCAM, tab-completion, storico a frecce persistito, un prompt con stato live del server (`● host` su / `○ offline` giù), un menu raggruppato `help` / `help <cmd>` e un built-in `watch [secs] <cmd>` che auto-aggiorna qualsiasi comando (es. `watch 5 kanban`); ogni riga gira come processo figlio isolato, così un rifiuto offline o un `tail` bloccante non buttano mai giù la shell. Se `ccam` non è nel tuo PATH (es. `npm link` richiedeva permessi elevati), esegui `npm link` una volta dalla root del repo. Riferimento completo — flag, ordine di discovery, il REPL, modello di sicurezza, scripting/exit code, risoluzione dei problemi — in [docs/CLI.md](./docs/CLI.md).

- Dashboard autenticata: imposta `MCP_DASHBOARD_API_TOKEN` / `_FILE` al token della dashboard
- Trasporto HTTP/SSE autenticato: imposta `MCP_HTTP_AUTH_TOKEN` / `_FILE`; i client inviano bearer auth o `x-mcp-token`
- Guardrail di trasporto: l'HTTP diretto in loopback può portare il token; gli alias container-host richiedono HTTPS; i redirect sono rifiutati

- Modalità distruttiva: richiede entrambi:
  - `MCP_DASHBOARD_ALLOW_MUTATIONS=true`
  - `MCP_DASHBOARD_ALLOW_DESTRUCTIVE=true`
  - input dello strumento `confirmation_token: "CLEAR_ALL_DATA"`

## Riferimento API

Tutti gli endpoint restituiscono JSON. Le risposte di errore seguono la forma `{ error: { code, message } }`.

### OpenAPI / Swagger / ReDoc

Ci sono tre modi per esplorare l'API HTTP, tutti guidati da un'unica spec OpenAPI 3.0.3 (porta di default del server `4820`):

| Metodo | Percorso                        | Descrizione                                                                                       |
| ------ | ------------------------------- | ------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/openapi.json`             | Spec JSON OpenAPI 3.0.3 grezza                                                                        |
| `GET`  | `/api/docs`                     | **Swagger UI** interattiva — esecuzione delle richieste try-it-out                                         |
| `GET`  | `/api/redoc`                    | Riferimento **ReDoc** — un rendering a tre pannelli pulito e ottimizzato per la lettura della stessa spec              |
| `GET`  | `/api/redoc/redoc.standalone.js`| Bundle ReDoc self-hosted (servito localmente via la dipendenza `redoc`, mai da CDN — funziona offline) |

Il documento OpenAPI è generato da `server/openapi.js` (`createOpenApiSpec()`), fuso con frammenti supplementari sotto `server/openapi-extra/`. Swagger UI e ReDoc sono entrambi serviti direttamente dal backend; il bundle ReDoc è servito localmente (`GET /api/redoc/redoc.standalone.js`) così il riferimento funziona completamente offline / air-gapped, coerentemente con la policy del progetto di zero asset esterni.

La copertura è completa: ogni route del backend è documentata (82 voci di percorso) attraverso questi tag — Health, Sessions, Agents, Events, Stats, Metrics, Analytics, Hooks, Pricing, Workflows, Settings, Updates, Alerts, Webhooks, Push, CcConfig (esploratore di configurazione di Claude Code), Run (esecuzioni avviate dalla dashboard) e Documentation — ciascuna con parametri, schemi di richiesta/risposta, descrizioni a livello di campo ed esempi realistici.

Un **`openapi.yaml`** committato alla root del repo rispecchia la spec live. È generato da `server/openapi.js` (mai modificato a mano) — rigeneralo dopo modifiche all'API con:

```bash
npm run openapi:yaml
```

### Metriche Prometheus e Grafana

`GET /api/metrics` espone i contatori live della dashboard — sessioni/agenti per stato, totali di eventi e token, client realtime connessi, sorgenti remote configurate, uptime/memoria del processo e versione di build — nel formato text-exposition di Prometheus, così CCAM può essere raccolto nel tuo stack di osservabilità. Uno stack Prometheus + Grafana chiavi in mano con **quattro dashboard auto-provisioned** (home di default: **CCAM — Overview**) vive in [`monitoring/`](./monitoring/README.md).

**npm (senza Docker — macOS, Linux o Windows):**

```bash
npm start                          # dashboard on :4820
npm run monitoring:install         # one-time: npm postinstall pulls binaries
npm run monitoring:up              # Grafana on :3000, auto-provisioned; see monitoring/README.md for credentials
```

**Docker / Podman** (quando la dashboard gira in un container o preferisci Compose):

```bash
# Dashboard only
npm run docker:up

# Dashboard + Prometheus + Grafana (one command)
npm run docker:full:up

# Or mix: native/docker dashboard + docker monitoring
DASHBOARD_ALLOWED_HOSTS=host.docker.internal npm start   # or docker:up with same env
npm run monitoring:docker:up
npm run monitoring:verify
```

### Run Claude (`/api/run`)

Superficie HTTP per avviare e supervisionare sottoprocessi `claude` dalla dashboard. Guardia same-origin su ogni route — le richieste dal browser devono provenire da un'origin localhost; le richieste senza Origin (CLI/curl) passano. Una `cwd` fornita deve essere una directory assoluta esistente ed è canonicalizzata con `realpath`. Intenzionalmente può essere fuori da questo repository così Run Agent può partire dalla home dell'utente o da qualsiasi progetto recente.

| Metodo   | Percorso                          | Descrizione |
| -------- | --------------------------------- | ----------- |
| `GET`    | `/api/run`                        | Elenca tutti gli handle di esecuzione in memoria (live + terminati di recente); restituisce anche `maxConcurrent` e `activeCount` |
| `GET`    | `/api/run/binary`                 | Sonda se `claude` è nel `PATH` e dove vive — usato dalla UI per mostrare un errore chiaro prima dello spawn |
| `GET`    | `/api/run/cwds`                   | Directory di lavoro suggerite: cwd del server della dashboard, `$HOME` e cwd recenti dalla tabella delle sessioni |
| `GET`    | `/api/run/files?cwd=…&q=…`        | Ricerca fuzzy di file dentro `cwd` per l'autocompletamento dei riferimenti `@`-file della pagina Run. Salta `node_modules`, `.git`, `dist`, `build`, `.next`, `.cache`, `coverage`, ecc. La cwd è obbligatoria e deve esistere; i risultati sono limitati e ordinati per match sul basename |
| `POST`   | `/api/run`                        | Avvia una nuova esecuzione. Body: `{ prompt, mode: "headless"\|"conversation", cwd?, model?, permissionMode?, resumeSessionId?, effort? }`. Headless mette il prompt in argv via `-p` e chiude lo stdin. Conversation invia il prompt sullo stdin come envelope stream-json e mantiene lo stdin aperto per i seguiti. `resumeSessionId` (solo conversation) aggiunge `--resume <id>`; quando impostato, `prompt` può essere vuoto — lo spawner salta la scrittura iniziale sullo stdin e `claude` resta in attesa sulla conversazione ripresa finché l'utente non invia un seguito via `POST /api/run/:id/message`. `effort` (`low` / `medium` / `high`) mappa su `--effort`. Lo spawner passa sempre `--output-format stream-json --verbose --include-partial-messages` così la UI può renderizzare i delta carattere per carattere. | `GET`    | `/api/run/:id`                    | Stato corrente dell'handle. `?envelopes=1` include il log degli envelope in memoria così la UI può rigiocare lo storico al ri-collegamento |
| `POST`   | `/api/run/:id/message`            | Invia un turno di seguito a una conversazione in esecuzione (solo modalità conversation). Body: `{ text }` |
| `DELETE` | `/api/run/:id`                    | Ferma un'esecuzione. SIGTERM, con escalation a SIGKILL dopo 5 s |

L'output fluisce sul WebSocket esistente della dashboard come tre tipi di messaggio: `run_stream` (envelope stream-json analizzato, inclusi i delta `stream_event` da `--include-partial-messages`), `run_status` (transizioni di stato), `run_input_ack` (scrittura sullo stdin confermata). La pagina Config Explorer si sottoscrive a un quarto messaggio — `cc_config_changed` — trasmesso da `server/lib/cc-watcher.js` (via `fs.watch` su `~/.claude/`) e da `routes/cc-config.js` dopo ogni PUT/DELETE riuscito, con payload `{ source: "dashboard"|"fs", action?, scope?, type?, name?, paths? }`. La lista Sessioni e la pagina SessionDetail interrogano `/api/run` (e ascoltano `run_status`) per contrassegnare qualsiasi sessione attualmente guidata da un'esecuzione in volo con un indicatore cliccabile **▶ Run** che rimanda a `/run`.

**Input supportati.** Trascrizioni di sessione JSONL sciolte (`.jsonl`), i loro
sidecar `.meta.json` di accompagnamento e archivi (`.zip`, `.tar`,
`.tar.gz`/`.tgz`, `.gz` semplice) contenenti qualsiasi layout di directory annidato.
Entrambi i layout canonici di Claude Code sono riconosciuti automaticamente:
`<project>/<sessionId>/subagents/agent-*.jsonl` (default) e
`<project>/subagents/<sessionId>/agent-*.jsonl` (alternativo).
Per Codex, l'importer riconosce ricorsivamente i file di sessione `rollout-*.jsonl`
(inclusi i file JSONL sciolti con `session_meta`) e un `session_index.jsonl`
opzionale per i nomi di sessione nativi.

**Garanzie di accuratezza.** Le sessioni sono deduplicate per UUID; rieseguire
l'importer è sempre sicuro. Le colonne di compattazione `baseline_input` /
`baseline_output` / `baseline_cache_read` / `baseline_cache_write`
preservano i conteggi dei token precedenti alla compattazione di una trascrizione,
così re-ingerire un JSONL post-compattazione non cancella mai il costo storico.
Il dedup a livello di evento usa un high-water mark per tipo di evento
(`MAX(created_at) GROUP BY event_type` per la sessione): a ogni
re-import vengono inserite solo le voci JSONL con `ts > cutoff[type]`, così
le sessioni di lunga durata le cui trascrizioni crescono per più giorni
continuano a ricevere eventi Stop / PostToolUse / TurnDuration / ToolError
senza duplicare il lavoro precedente. `sessions.ended_at` viene fatto avanzare
all'ultima attività del JSONL quando supera il valore salvato,
e i metadata del conteggio dei messaggi sono aggiornati a ogni passaggio.

**Sicurezza per trascrizioni enormi.** La cache delle trascrizioni condivisa
(`server/lib/transcript-cache.js`) legge i file JSONL in chunk da 4 MiB
e decodifica una sola riga alla volta, così le trascrizioni più grandi della
lunghezza massima di stringa JS di V8 (~512 MiB su Node 20 a 64 bit) vengono analizzate senza
abortire il processo con `FATAL ERROR: v8::ToLocalChecked Empty
MaybeLocal`. Lo stesso percorso a chunk è usato dall'ingestione degli hook, dallo
sweep periodico delle compattazioni e dall'importer dello storico — nessuno di loro
materializza il file completo come una singola stringa JS. Gli array crescenti
per voce (`turnDurations`, `errors`, `compaction.entries`,
`usageExtras.*`) sono limitati in coda a `TRANSCRIPT_CACHE_MAX_ARRAY_LEN`
(default `1000`), con il trimming applicato durante il parse a una soglia di `2 × cap`
così un parse completo a freddo di una sessione multi-giorno non può
costruire un transiente illimitato prima della finalizzazione.

**Sicurezza.** L'estrazione degli archivi valida ogni voce contro il path
traversal (percorsi assoluti e segmenti `..` sono rifiutati). Un
limite di estrazione configurabile (`CCAM_IMPORT_MAX_EXTRACT_BYTES`, default
4 GB) ferma le bombe zip/tar/gzip. La dimensione degli upload è limitata per file
(`CCAM_IMPORT_MAX_BYTES`, default 1 GB) e per richiesta
(`CCAM_IMPORT_MAX_FILES`, default 2000). Tutte le directory di staging sono
per richiesta e recuperate in `finally`, anche quando multer rifiuta
tutti i file in partenza.

**Avanzamento.** L'attività di import è trasmessa sul WebSocket esistente
come messaggi `import.progress` (`phase`: `start` / `scan` / `extract` /
`parse` / `complete` / `error`), con throttling per evitare di inondare il
canale sugli import grandi.

**UI.** Usa il pannello **Impostazioni → Import History** per un'esperienza guidata
drag-and-drop con istruzioni passo passo, avanzamento live
e un riepilogo post-import che mostra i conteggi di importati / arricchiti / saltati /
in errore.

| `Notification`      | Notifica dell'agente             | Registra l'evento. | `SessionEnd`        | Il processo CLI di Claude Code esce  | Rimuove il flag di attesa. Se la sessione è già in `error`, lo stato di errore viene preservato; altrimenti marca tutti gli agenti e la sessione come `completed` |

## Notifiche del browser

La dashboard supporta notifiche del browser persistenti via Web Push (VAPID) per avvisi in tempo reale anche quando la scheda della dashboard non è a fuoco o il browser è in background.

### Come funziona

1. **Abilita** le notifiche nella pagina Impostazioni tramite l'interruttore generale
2. **Concedi** il permesso del browser quando richiesto — questo registra un Service Worker e crea una sottoscrizione push
3. **Configura** quali eventi innescano le notifiche:

| Evento                       | Default | Descrizione                                                     |
| ---------------------------- | ------- | --------------------------------------------------------------- |
| Nuova sessione avviata           | On      | Scatta quando viene creata una nuova sessione Claude Code                 |
| Claude ha finito di rispondere   | Off     | Scatta sugli eventi `Stop` quando Claude finisce un turno di risposta     |
| Sessione chiusa               | Off     | Scatta al `SessionEnd` quando il processo CLI esce                |
| Errori di sessione               | On      | Scatta quando una sessione termina con un errore                         |
| Subagente generato             | Off     | Scatta quando viene creato un subagente in background                     |

Inoltre, qualsiasi evento hook `Notification` da Claude Code innesca una notifica del browser indipendentemente dagli interruttori per evento (finché l'interruttore generale è abilitato).

### Architettura delle notifiche

- **Pipeline VAPID:** usa `web-push` sul server per una consegna sicura dei messaggi. Le chiavi VAPID sono auto-generate e salvate in `data/vapid-keys.json`.
- **Service Worker:** un worker dedicato (`client/public/sw.js`) gestisce gli eventi `push` in arrivo e mostra le notifiche con `silent: false` per garantire la riproduzione audio su macOS.
- **Sottoscrizioni:** gli endpoint specifici del browser sono salvati nella tabella `push_subscriptions` di SQLite.
- **Persistenza:** le notifiche arrivano anche se il browser è chiuso, dato che il Service Worker opera in background.
- **Notifica di test:** un pulsante nelle Impostazioni ti permette di verificare la pipeline VAPID e la riproduzione audio.

### PWA e supporto offline

Il progetto include tre Progressive Web App indipendenti — una ciascuna per **dashboard**, **landing page** e **wiki**. Ognuna ha il proprio `manifest.json` e Service Worker così il browser le tratta come applicazioni installabili separate.

| Superficie | Manifest | Service Worker | Strategia di caching |
| --- | --- | --- | --- |
| Dashboard (`client/`) | `client/public/manifest.json` | `client/public/sw.js` | I bundle con hash nel contenuto di Vite sotto `/assets/*` sono serviti cache-first (gli URL sono immutabili per build). Tutto il resto — navigazioni, il SW stesso, `manifest.json`, icone, la root `/` — è network-first con fallback sulla cache, così una rebuild mostra sempre la UI più fresca senza hard refresh. Le richieste API (`/api/*`), WebSocket (`/ws`) e Vite HMR non sono mai cachate. I gestori delle notifiche push sono preservati accanto alla logica di caching. Il middleware statico Express (`server/index.js`) rinforza questo inviando `Cache-Control: public, max-age=31536000, immutable` per `/assets/*` e `Cache-Control: no-cache, must-revalidate` per `index.html`, `sw.js` e `manifest.json`. `client/src/main.tsx` ascolta `controllerchange`: quando un nuovo SW si attiva su una pagina già controllata ricarica esattamente una volta (le prime installazioni no). |
| Landing page (root) | `manifest.json` | `sw.js` | Precache della shell HTML, del favicon e dell'immagine OG. I PNG degli screenshot sono cachati pigramente alla prima vista (cache-first) per evitare un precache iniziale pesante. La navigazione è network-first con fallback offline. |
| Wiki (`wiki/`) | `wiki/manifest.json` | `wiki/sw.js` | Precache di `index.html`, `style.css`, `script.js`, manifest e favicon. Completamente utilizzabile offline dopo una visita. HTML network-first, CSS/JS cache-first. |

**Ciclo di vita della cache:** tutti e tre i SW chiamano `skipWaiting()` all'installazione ed eliminano le cache stantie all'attivazione (con chiavi di versione come `dashboard-v2`, `landing-v1`, `wiki-v1`). Incrementare la costante di versione forza un refresh pulito.

**Supporto iOS:** tutti e tre i file HTML includono `<meta name="apple-mobile-web-app-capable" content="yes">` e `<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">` per la modalità standalone da home screen su Safari.

**Icone:** i manifest referenziano `favicon.svg` con `sizes="any"` e `type="image/svg+xml"` — supportato in Chrome 107+, Firefox 110+, Edge 107+. Anche le Apple touch icon usano il favicon SVG.

## Notificatore di aggiornamenti

La dashboard osserva il proprio checkout git e mostra una modale ogni volta che il branch di default canonico ha commit avanti rispetto a HEAD. **Consapevole di branch e fork:** se hai un remote `upstream` (la convenzione standard per i fork), è preferito a `origin`; il `master`/`main`/`HEAD` del remote scelto è il ref di confronto. Il `manual_command` si adatta alla tua situazione — `git pull --ff-only` solo quando il tuo branch traccia effettivamente il ref canonico, altrimenti un `git fetch` (e un merge fast-forward nel caso del fork) così il comando non mente mai. Gli utenti ricevono il comando esatto da eseguire in un terminale — il server non fa **mai** pull né si riavvia da solo, il che mantiene il meccanismo portabile attraverso sessioni di sviluppo, supervisione pm2/systemd/launchd/Docker e deployment remoti.

### Come funziona

```mermaid

```

Un singolo controllo è economico (`git fetch <remote> --prune` contro il remote canonico — `upstream` se configurato, altrimenti `origin`), incapsulato con `execFile` (nessuna shell) e un timeout di 120 s. I fallimenti — rete offline, installazione non-git, nessun remote configurato, ref upstream non risolvibile — restituiscono tutti **payload soft** (es. `fetch_error: "..."`) invece di lanciare eccezioni, così un remote instabile non blocca mai la dashboard.

### Superfici UI

| Superficie | Comportamento |
| --- | --- |
| **Modale** (`client/src/components/UpdateNotifier.tsx`) | Appare quando `update_available === true` e l'utente non ha già scartato questo specifico `remote_sha`. Mostra i commit di ritardo, il ref tracciato, una `situation_note` opzionale (quando si è su un feature branch / fork la nota spiega perché il comando differisce), il comando copiabile e tre pulsanti: **Copy command** (primario), **Check now**, **Dismiss**. ESC e i click sul backdrop la chiudono. Con chiave `remote_sha` in `localStorage`, così un commit upstream più recente riapre la modale automaticamente. |
| **Pulsante nella sidebar** (`client/src/components/Sidebar.tsx`) | Pulsante "Check for updates" sempre visibile nel footer. Bordo smeraldo + puntino badge verde quando si è indietro, ambra quando l'ultimo controllo ha incontrato un errore di fetch. Cliccarlo cancella qualsiasi scarto precedente, poi lancia `POST /api/updates/check`. |
| **Terminale del server** | Quando lo scheduler transisce da "aggiornato" a "indietro", stampa un blocco incorniciato su stdout con il comando così anche gli utenti headless lo vedono. |

### Superficie API

| Endpoint | Scopo |
| --- | --- |
| `GET /api/updates/status` | Controllo di sola lettura: esegue `git fetch` contro il remote canonico, confronta HEAD con il suo branch di default, restituisce il payload. |
| `POST /api/updates/check` | Stesso controllo, ma trasmette anche `update_status` sul WebSocket così tutti i client connessi si aggiornano insieme. |

Entrambi gli endpoint restituiscono la stessa forma di payload:

```json
{
  "git_repo": true,
  "update_available": true,
  "repo_root": "/Users/you/Claude-Code-Agent-Monitor",
  "remote_ref": "upstream/master",
  "canonical_remote": "upstream",
  "current_branch": "master",
  "tracking_upstream": "origin/master",
  "tracks_canonical": false,
  "situation": "fork_or_diverged_tracking",
  "local_sha": "abc1234...",
  "remote_sha": "def5678...",
  "commits_behind": 3,
  "manual_command": "cd \"/...\" && git fetch upstream && git merge --ff-only upstream/master && npm run setup",
  "situation_note": "You're on 'master' tracking 'origin/master'. This command fast-forwards your branch from upstream/master (the canonical default).",
  "message": "3 commit(s) on upstream/master not in your checkout."
}
```

`situation` è uno tra `tracking_canonical` (clone tipico sul branch di default — `git pull --ff-only` funziona), `fork_or_diverged_tracking` (il nome del branch locale corrisponde al canonico, ma traccia un remote diverso — `git fetch <remote> && git merge --ff-only <ref>`), `feature_branch` (fuori dal branch di default — solo fetch, l'integrazione è lasciata all'utente) o `detached_head`.

### Cosa **non** c'è, intenzionalmente

Non esiste un `POST /api/updates/apply` né un helper di auto-riavvio, per scelta. Auto-aggiornare un processo dal suo interno è inaffidabile senza un supervisore esterno — `npm run dev` (concurrently), `npm start`, `pm2`, `systemd`, `launchd` e Docker richiedono ciascuno una logica di riavvio diversa, e i fallimenti di `git pull` / `npm install` su un server morente non hanno un percorso di rollback pulito. Il solo rilevamento mantiene il comportamento prevedibile con ogni supervisore, ogni OS e ogni stato del branch, chiudendo comunque il gap informativo del "quando devo fare pull?"; l'aggiornamento vero e proprio è dell'utente, nella sua shell.

### Configurazione

| Variabile d'ambiente | Default | Note |
| --- | --- | --- |
| `DASHBOARD_UPDATE_CHECK` | abilitato | Imposta `0` / `false` / `off` per disabilitare interamente lo scheduler. |
| `DASHBOARD_UPDATE_CHECK_INTERVAL_MS` | `300000` (5 min) | Intervallo tra i controlli automatici. Il minimo è 60 000 ms — i valori inferiori vengono limitati. |

### Mascotte reattiva

Tabby è un gatto SVG che segue il cursore con **otto stati d'animo** derivati dallo stream live delle sessioni, ognuno con la propria animazione:

| Stato d'animo | Quando | Animazione |
| --- | --- | --- |
| `idle` | Non succede nulla di rilevante | Colpo di coda a riposo |
| `watching` | Ci sono sessioni attive | Orecchie dritte, gli occhi seguono il cursore |
| `happy` | Una sessione o esecuzione è finita pulita | Testa che ondeggia + scintillio |
| `worried` | Qualcosa sembra storto | Scossa sottile |

| `thinking` | Un agente è a metà lavoro | Lenta oscillazione della testa |
| `sleeping` | Silenzio da un po' | `zzz` |
| `disconnected` | Il WebSocket è giù | Posa calma e immobile |

### Fumetti

Tabby fa emergere automaticamente brevi battute sugli eventi rilevanti (sessione avviata/terminata, errori, esecuzione completata). I fumetti sono **limitati e coalizzati** così una raffica di eventi non riempie mai lo schermo, usano `aria-live` per gli screen reader e possono essere **silenziati** dal pannello.

### Pannello

Apri il pannello cliccando il gatto o premendo **⌘B / Ctrl+B** (Esc chiude). Mostra:

- Una **riga di stato** live — `N live · M errored · stato della connessione`.
- **Azioni rapide** — salta a Run Claude, Attività, Sessioni o alle sessioni in errore; silenzia i fumetti; cancella gli alert.
- Una casella **Ask** (vedi sotto).

### Casella Ask → passaggio a Run Claude

La casella **Ask** risponde alle semplici domande di stato localmente dai dati in cache — per esempio "what's running", "any errors" o "status". Qualsiasi altra domanda viene passata alla pagina **Run Claude** esistente (con deep-link a `/run?prompt=…`) per avviare una vera sessione Claude Code. Tabby non chiama mai un LLM da solo; riusa semplicemente la pagina Run Claude per qualsiasi cosa oltre un rapido controllo di stato.

### Accessibilità e degradazione sicura

Tabby è utilizzabile da tastiera, usa `aria-live` per i suoi fumetti e rispetta `prefers-reduced-motion`. Se il WebSocket è giù degrada in sicurezza a uno stato calmo `disconnected` invece di andare in errore. Puoi attivare o disattivare Tabby nelle **Impostazioni** (localizzato in inglese, cinese, vietnamita, coreano, spagnolo e italiano), e l'implementazione vive in `client/src/components/Tabby/`.

## Segnali sonori

La dashboard ti dà un **feedback audio discreto** per l'attività live delle sessioni, così puoi lasciarla su un secondo monitor e sentire comunque quando un'esecuzione finisce o fallisce. Il suono è **attivo per default** e può essere spento del tutto in un click.

### Sintesi a zero dipendenze

Non ci sono asset `.mp3` o `.wav` da nessuna parte nel repo e nessuna libreria audio in `package.json`. Ogni segnale è generato al momento della riproduzione con la **Web Audio API**: una breve lista di oscillatori (sinusoide o triangolo), ognuno con il proprio inviluppo di gain esponenziale, mixati attraverso un nodo di gain master e un filtro passa-basso così il risultato resta dietro al tuo lavoro invece di tagliarlo. L'intero motore è un solo file, `client/src/lib/sound.ts`.

### I segnali

| Segnale | Quando scatta | Come suona |
| --- | --- | --- |
| `sessionStart` | Appare una nuova sessione | Quinta giusta ascendente (C5 → G5) |
| `sessionComplete` | Una sessione finisce di rispondere (`Stop`) o si chiude (`SessionEnd`) | Arpeggio maggiore risolutivo (E5 → G5 → C6) |
| `sessionError` | Una sessione entra nello stato `error` | Morbida terza minore discendente su un'onda triangolare — udibile, non allarmante |
| `subagentSpawn` | Viene generato un subagente | Singolo pizzicato corto |
| `notification` | Claude Code emette un evento `Notification` | Coppia scordata che risuona come una piccola campana |
| `connected` / `disconnected` | Il WebSocket della dashboard torna o cade | Due note in salita / discesa |
| `click` | Premi un pulsante, link, scheda o interruttore | Tick appena udibile |

I segnali vivono dentro un set in Do maggiore così le code sovrapposte non suonano mai dissonanti, e ogni inviluppo decade esponenzialmente invece di troncarsi, evitando il click di uno stop brusco.

### Restare fuori dai piedi

Tre guardie impediscono all'audio di diventare rumore:

- **Cooldown per segnale** — lo stesso segnale non si ripete entro ~350 ms (45 ms per il tick di interazione).
- **Budget globale di burst** — al massimo 4 segnali partono in una finestra di 1,2 s, così importare lo storico o riconnettersi dopo una caduta non trasforma mai un fiume di messaggi WebSocket in un fiume di bip.
- **Policy di autoplay** — nulla suona fino alla tua prima interazione con la pagina via puntatore, tasto o tocco, come da regole del browser. I segnali precedenti vengono scartati in silenzio, non accodati.

Se il browser non ha alcun supporto Web Audio, ogni chiamata è un no-op sicuro — la dashboard resta semplicemente silenziosa.

### Impostazioni

**Impostazioni → Sound** ha un interruttore generale, uno slider del volume e un interruttore individuale per ogni segnale. Attivare un interruttore riproduce quel segnale immediatamente così senti esattamente cosa hai appena abilitato, e un pulsante **Preview Sound** riproduce il carillon di completamento su richiesta. Le preferenze persistono in `localStorage` sotto `agent-monitor-sound` e hanno effetto istantaneo in tutta l'app — nessun reload. Il pannello è localizzato in inglese, cinese, vietnamita, coreano, spagnolo e italiano.

Per default sono attivi avvio sessione, completamento sessione, errore di sessione, le notifiche di Claude Code e il tick di interazione; gli spawn di subagenti e i cambi di connessione sono spenti (sono i più chiacchieroni). L'implementazione vive in `client/src/lib/sound.ts` (motore + preferenze) e `client/src/hooks/useSoundCues.ts` (collegamento all'event bus), montata una volta in `client/src/App.tsx`.

### Come funziona

A differenza dell'esecuzione della dashboard da un terminale, l'app desktop non richiede `npm start`, nessuna shell aperta e nessuna seconda copia del server. Il **processo main** di Electron ospita il server Express **in-process** — fa `require()` di `server/index.js` direttamente nello stesso runtime Node, **senza processo figlio e senza IPC** — e punta una `BrowserWindow` Chromium al client React compilato.

Al lancio l'app:

1. Sceglie una porta libera — preferendo la **4820**, ripiegando su **4821–4829**, poi su una porta alta casuale se sono tutte occupate.
2. Se una dashboard in salute risponde già a `/api/health` sulla `4820` (es. hai eseguito `npm start` in un terminale), **adotta quel server** invece di fare doppio binding — nessuna collisione di porta, nessuna contesa su SQLite. Un server adottato continua a girare dopo che chiudi l'app.
3. Altrimenti avvia il server incorporato, e al **primo boot con server di proprietà** installa automaticamente gli hook di Claude Code e avvia i servizi in background (scheduler degli aggiornamenti, `cc-watcher`, riconciliazione delle esecuzioni orfane). Un utente solo-DMG ottiene quindi il flusso di eventi con **zero configurazione manuale** — nessun checkout, nessun `npm run install-hooks`.
4. **(macOS)** Recupera il **`PATH` della tua shell di login** così la funzionalità **Run Claude** può trovare e avviare la CLI `claude` — un'app lanciata da Finder/Dock altrimenti eredita solo il `PATH` minimale di launchd e mancherebbe le CLI in `~/.local/bin`, `/opt/homebrew/bin`, i bin dei version manager, ecc. (Su Windows il processo eredita già il `PATH` dell'utente.)
5. Apre la finestra della dashboard — a meno che l'app non sia stata lanciata al login (su macOS via Login Items; su Windows via la voce taggata `HKCU\…\Run`), nel qual caso resta solo nel tray.
6. All'uscita, spegne con grazia il server incorporato e **chiude SQLite in modo pulito** (checkpoint WAL).

### Funzionalità

- **Icona tray** — superficie di stato sempre attiva (barra dei menu macOS / area di notifica Windows). Il click sinistro commuta la finestra della dashboard; il click destro apre un menu contestuale con **Open Dashboard**, **Open in Browser**, **Restart Server**, **Show Logs**, **Open at Login** (toggle) e **Quit**. macOS usa un glifo template tinteggiato; Windows usa l'`icon.ico` colorato (un template nero sparirebbe sulla taskbar scura).
- **Icona di finestra e taskbar** — la `BrowserWindow` è collegata al logo colorato dell'app (`icon.ico` su Windows, `icon.png` altrove), così barra del titolo / taskbar mostrano la vera icona di Claude Code Monitor — persino un'esecuzione non impacchettata `npm run desktop:dev` non mostra più l'icona generica di Electron.
- **Menu applicazione nativo** — menu standard `About` / `File` / `Edit` / `View` / `Window` / `Help` con scorciatoie `⌘` / `Ctrl`. La voce **File → Open Dashboard** (`⌘1`) è **solo macOS**: macOS mantiene una barra dei menu globale dopo che la finestra si nasconde, quindi può riaprirla — su Windows/Linux il menu è attaccato alla finestra e non può scattare mentre è nascosta, quindi riaprila dal **Open Dashboard** del tray (che rialza in modo affidabile la finestra anche quando è minimizzata o dietro altre finestre).
- **Avvio automatico al login** — commuta **Open at Login** dal tray o dal menu dell'app. Su macOS si registra tramite la moderna API `SMAppService`, così la voce appare sotto **Impostazioni di Sistema → Generali → Elementi login**; su Windows scrive una voce per utente `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, visibile in **Gestione attività → Avvio**.
- **La chiusura della finestra nasconde, il server continua a girare** — chiudere la finestra la nasconde soltanto; server e tray restano su. Clicca il tray per far tornare la finestra.
- **Lock a istanza singola** — un doppio lancio si limita a portare a fuoco la finestra esistente; nessun secondo server, nessuna collisione di porta. (Vale su ogni piattaforma.)
- **I dati sopravvivono a reinstallazioni e aggiornamenti** — il database SQLite e le chiavi VAPID vivono nella directory app-data per utente **fuori dal bundle dell'app / directory di installazione** — `~/Library/Application Support/Claude Code Monitor/data/` su macOS, `%APPDATA%\Claude Code Monitor\data\` su Windows. Un bundle impacchettato è read-only, quindi scrivere il database al suo interno romperebbe l'Import History e la persistenza degli eventi; tenerlo in app-data lo risolve e significa che il tuo storico importato resta intatto quando sostituisci o aggiorni l'app. (L'uninstaller NSIS di Windows conserva questi dati per default.)
- **La CLI `claude` nel PATH** — su macOS l'app recupera all'avvio il `PATH` della tua shell di login, così la funzionalità **Run Claude** funziona anche se un'app lanciata da Finder/Dock erediterebbe altrimenti solo il `PATH` minimale di launchd. (Su Windows il `PATH` utente ereditato lo include già.)
- **Log** — il processo main scrive in `~/Library/Logs/Claude Code Monitor/desktop.log` (macOS) o `%APPDATA%\Claude Code Monitor\logs\desktop.log` (Windows); raggiungilo da **Show Logs** nel menu del tray.

Per il tuo Mac usa i single-arch `desktop:dmg:arm64` / `desktop:dmg:x64`. Se la build fallisce comunque (nessun binario precompilato, o toolchain C++ mancante), `desktop:install` stampa la correzione esatta per sistema operativo più un'alternativa senza toolchain e fallisce rumorosamente invece di lasciare un'installazione rotta.

### Comandi di build

Tutti i comandi si eseguono dalla **root del repo**:

| Comando                     | Cosa fa                                                                 |
| --------------------------- | ---------------------------------------------------------------------------- |
| `npm run desktop:install`   | Installa Electron + electron-builder in `desktop/`; ricompila `better-sqlite3` per l'ABI di Electron; verifica preventivamente la build nativa di `better-sqlite3` e stampa aiuto pratico di setup (incl. un'alternativa senza toolchain) in caso di fallimento |
| `npm run desktop:build`     | Compila i sorgenti TypeScript desktop in `desktop/out/`                    |
| `npm run desktop:dev`       | Compila e lancia l'app Electron per l'iterazione locale                         |
| `npm run desktop:test`      | Esegue lo smoke test (avvia Electron, sonda `/api/health`, spegne)            |
| `npm run desktop:dmg`       | **macOS:** compila **entrambi** i DMG (arm64 + x64) — corretto per le release, **più lento** (impacchetta ogni arch) |
| `npm run desktop:dmg:arm64` | **macOS:** compila un DMG solo Apple Silicon — **veloce** (~1 min), consigliato per il tuo Mac |
| `npm run desktop:dmg:x64`   | **macOS:** compila un DMG solo Intel — **veloce** (~1 min)                         |
| `npm run desktop:dmg:universal` | **macOS:** compila un unico DMG **universale** fuso (arm64 + x86_64) — opzionale, **il più lento**, non quello distribuito nelle release |
| `npm run desktop:win`       | **Windows:** compila l'installer NSIS `.exe` (x64)                             |
| `npm run desktop:win:portable` | **Windows:** compila il portable senza installazione `.exe` (x64)                     |

Il DMG macOS risultante è di **~80 MB** (≈ 250 MB su disco una volta installato) e l'installer Windows è paragonabile — la classica tassa del bundle Electron.

### Firma e notarizzazione

Il DMG macOS è **firmato ad-hoc** per default così chiunque può compilare una `.app` funzionante senza un account Apple Developer a pagamento — lo script `package` imposta `CSC_IDENTITY_AUTO_DISCOVERY=false` così un certificato di code-signing già nel portachiavi del contributor non viene mai auto-selezionato. La vera **firma Developer ID** è opt-in via `CSC_LINK` (un `.p12` codificato base64) e `CSC_KEY_PASSWORD`; la **notarizzazione Apple** è opt-in via `APPLE_ID`, `APPLE_TEAM_ID` e `APPLE_APP_SPECIFIC_PASSWORD`. La build **Windows** è **non firmata** per default (SmartScreen può avvisare al primo lancio — *More info → Run anyway*); la firma Authenticode si attiva solo quando un certificato esplicito è fornito via `CSC_LINK` + `CSC_KEY_PASSWORD`. La CI li raccoglie tutti automaticamente quando forniti — nessuna modifica al codice richiesta.

### Note di implementazione

- **`better-sqlite3`** è l'unico modulo nativo nell'albero delle dipendenze, e un modulo nativo va compilato contro l'esatta ABI Node su cui gira. Il workspace `desktop/` include la **propria copia** di `better-sqlite3` ricompilata per l'ABI di Electron e usa un redirect di `require` locale al processo per puntare `server/db.js` verso di essa; la copia alla root del repo resta compilata per il Node di sistema (così `npm run test:server` continua a funzionare).
- **Compilare un DMG ricompila `better-sqlite3` per l'architettura target**, il che può lasciare la copia desktop compilata per l'altra arch della CPU e rompere `npm run desktop:dev` / `npm run desktop:test` con `ERR_DLOPEN_FAILED`. Lo step `prebuild` desktop ora **auto-ripara** il modulo nativo per la macchina locale alla build successiva, così i flussi di dev e smoke-test continuano a funzionare dopo una build DMG specifica per arch. Lo step `prebuild` inoltre **fallisce subito con aiuto di setup** quando il binario nativo di `better-sqlite3` manca del tutto, trasformando un crash a runtime in un errore di build copiabile.
- L'**unica modifica fuori da `desktop/`** è un refactor senza cambi di comportamento di `server/index.js`: il suo bootstrap post-listen (scheduler degli aggiornamenti, `cc-watcher`, riconciliazione delle esecuzioni orfane) è stato estratto in una `startBackgroundServices()` esportata così il server incorporato esegue esattamente ciò che esegue `node server/index.js`. Il percorso standalone `node server/index.js` è funzionalmente invariato; `client/`, `scripts/`, `mcp/` e `vscode-extension/` sono intoccati.
- Due job CI desktop filtrati per percorso compilano, testano e impacchettano l'app: **`🍎 macOS Desktop (DMG)`** su `macos-latest` (carica l'artifact `ClaudeCodeMonitor-dmg` — due DMG single-arch) e **`🪟 Windows Desktop (EXE)`** su `windows-latest` (carica l'artifact `ClaudeCodeMonitor-win` — installer NSIS + portable). A un push con incremento di versione su `master`, il job `release` allega **sia** i DMG macOS **sia** gli `.exe` Windows alla Release GitHub `vX.Y.Z` pubblicata. L'icona Windows (`desktop/assets/icon.ico`) è committata nel repo (rigenerala da `icon.png` con `npm run build:win-icon`, PowerShell + .NET, nessun tooling extra).

Per la guida utente completa (download, installazione, Gatekeeper / SmartScreen, menu del tray, avvio automatico) vedi [`DESKTOP.md`](./DESKTOP.md); per il riferimento contributor / architettura (modello di processo, ciclo di vita del boot, discovery della porta, pipeline di build — con diagrammi Mermaid) vedi [`desktop/README.md`](./desktop/README.md).

## Marketplace dei plugin

CCAM distribuisce **14 plugin** da un unico albero sorgente condiviso. Claude Code legge `.claude-plugin/marketplace.json`; Codex legge `.agents/plugins/marketplace.json` più il `.codex-plugin/plugin.json` di ciascun plugin. Il bundle contiene **66 skill di plugin, 18 subagenti Claude, 34 comandi Claude, 3 helper CLI, 3 configurazioni di hook e 2 plugin abilitati MCP**.

```bash
# Claude Code
claude plugin marketplace add hoangsonww/Claude-Code-Agent-Monitor
claude plugin install ccam-platform@claude-code-agent-monitor-plugins

# Codex
codex plugin marketplace add hoangsonww/Claude-Code-Agent-Monitor
codex plugin add ccam-platform@claude-code-agent-monitor-plugins

# Open Agent Skills / skills.sh-compatible CLI
npx skills add hoangsonww/Claude-Code-Agent-Monitor --list

# Install one skill for Claude Code and Codex in the current project
npx skills add hoangsonww/Claude-Code-Agent-Monitor \
  --skill mcp-server \
  --agent claude-code \
  --agent codex \
  --yes

# Verify, update, and remove the project-scoped skill
npx skills list --json
npx skills update --project --yes
npx skills remove mcp-server --yes

# Add --global to install at user scope, then manage that scope explicitly
npx skills add hoangsonww/Claude-Code-Agent-Monitor \
  --skill mcp-server \
  --agent claude-code \
  --agent codex \
  --global \
  --yes
npx skills list --global --json
npx skills update --global --yes
npx skills remove --global mcp-server --yes
```

La CLI `skills` scopre **76 skill totali del repository**, incluse le 66 skill dei plugin e le skill di manutenzione del repository. Le installazioni di progetto usano `.agents/skills/` più link specifici per agente. Le skill globali di Claude Code vanno per default in `~/.claude/skills/`, o in `$CLAUDE_CONFIG_DIR/skills/` quando impostata. Le skill globali di Codex vanno per default in `~/.codex/skills/`, o in `$CODEX_HOME/skills/` quando impostata. Le installazioni multi-agente possono deduplicare i file tramite uno store condiviso e linkare quelle destinazioni. Ogni skill di plugin ha frontmatter canonico `name`/`description` e metadata `agents/openai.yaml`. Nessuna PR upstream verso `vercel-labs/skills` è necessaria per l'installazione. Il repository GitHub pubblico è la sorgente, e la visibilità su skills.sh segue la pubblicazione e la telemetria di installazioni reali.

### Deployment in cloud

Lo stack `deployments/` punta a qualsiasi servizio Kubernetes conforme, inclusi EKS, GKE, AKS, OKE e i cluster self-managed. CCAM usa SQLite, quindi ogni manifest supportato impone **un solo writer attivo della dashboard per volume persistente** con un rollout Recreate. HPA, repliche active-active, blue-green e canary sono intenzionalmente non supportati finché SQLite resta il backend di persistenza.

```mermaid
flowchart LR
  CI["CI: test · validate · scan · attest · sign"] --> HELM["Helm / Kustomize / Terraform"]
  HELM --> APP["CCAM dashboard<br/>exactly 1 replica"]
  APP --> PVC[("Retained ReadWriteOnce PVC")]
  EDGE["Ingress or Gateway API<br/>TLS + WebSocket"] --> APP
  PROM["Prometheus Operator"] -->|"Bearer /api/metrics"| APP
  MCP["Authenticated MCP sidecar"] --> APP
```

- **Helm:** un solo writer imposto dallo schema, supporto ai digest, PVC conservato, Ingress o Gateway API, mount del token compatibile con External-Secret, NetworkPolicy, MCP e ServiceMonitor opzionali.
- **Kustomize:** base con PSS restricted più overlay dev/staging/production e componenti opzionali per MCP, monitoring, Gateway API e snapshot CSI.
- **Terraform:** distribuisce il chart Helm validato su un cluster Kubernetes esistente. Networking cloud, identità del cluster, CSI, TLS e sincronizzazione dei segreti restano di competenza del provider.
- **Operazioni:** backup online SQLite coerente con SHA-256, ripristino verificato con scale-to-zero, deploy/rollback/teardown backup-first e health check autenticati.
- **Supply chain CI:** le immagini app e MCP sono scansionate, pubblicate per amd64/arm64 con SBOM e provenance SLSA, e firmate keyless con Cosign.

## Risoluzione dei problemi

| Problema                          | Soluzione                                                                                                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `better-sqlite3` non si installa | Non è fatale — il server ripiega automaticamente sul `node:sqlite` integrato di Node.js (Node 22+). Su versioni di Node più vecchie, installa Python 3 e gli strumenti di build C++, poi esegui `npm rebuild better-sqlite3` |
| Gli hook non scattano                  | Esegui `npm run install-hooks` e riavvia Claude Code. Verifica che gli hook esistano in `~/.claude/settings.json`                                                             |
| La dashboard non mostra dati           | Assicurati che il server sia in esecuzione (`npm run dev`) prima di avviare una sessione Claude Code. Controlla `http://localhost:4820/api/health`                                     |
| WebSocket disconnesso            | Il client si riconnette automaticamente ogni 2 secondi. Controlla che la porta 4820 non sia bloccata da un firewall                                                                    |
| Dati stantii dopo un riavvio          | Il database persiste tra i riavvii. Esegui `npm run seed` per dati demo freschi, o elimina `data/dashboard.db` per resettare                                            |
| Gli strumenti MCP non si connettono         | Conferma che l'API della dashboard sia su all'indirizzo `MCP_DASHBOARD_BASE_URL` e ricompila/avvia MCP (`npm run mcp:build`, `npm run mcp:start`)                                         |
